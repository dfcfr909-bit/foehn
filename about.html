山に行く日を決めるための
天気予報アプリです

1時間ごとの予報を、実績3日ぶんと合わせて指でなぞって見ます。 その時刻が ABC のどれかを出しますが、「なぜそうなのか」がグラフの上で読めるように作ってあります。

アプリを開く ソースを見る

⚠ 先に読んでほしいこと

  • これは予報であって、保証ではありません。気象庁のモデルの計算結果をそのまま表示しています。
  • A / B / C はあくまで目安です。数値をいくつかの閾値と比べているだけで、 現地の地形・積雪・体力・装備・同行者は一切見ていません。
  • 山の天気は急変します。とくに稜線の風は、麓の予報からは想像がつきません。
  • 最終的な判断は必ずご自身で。このアプリが A を出していても、 引き返す理由はいくらでもあります。

1. A / B / C はどう決まるか

5つの項目をそれぞれ A・B・C で採点し、いちばん悪かった項目がその時刻の判定になります。 平均は取りません。ひとつでも C があれば C です。

項目ABC
風速
山頂の高さの風		 5 m/s 未満5 〜 10 m/s10 m/s 以上
体感温度 -3℃ より上-15 〜 -3℃-15℃ 以下
降雪 0.5 cm/h 未満0.5 〜 2 cm/h2 cm/h 以上
降水 1 mm/h 未満1 〜 3 mm/h3 mm/h 以上
気圧の変化
6時間での増減		 6 hPa 未満6 〜 10 hPa10 hPa 以上

降雪と降水は、降っているときだけ採点に入ります（0 のときは判定に影響しません）。 気圧は上がる側も下がる側も、変化の大きさだけを見ます。

グラフの上で判定の理由が読めます

  • 風 — バーの色が閾値で変わります
  • 降水・降雪 — バーの縁が 橙（B） 赤（C）になります
  • 体感温度 — 気温グラフの下端の細い帯。 寒いほど濃い青になり、B・C の時間は枠で囲みます

体感温度の帯は、寒い側だけ濃くしてあります。

暑い側にも同じだけ色を振ったところ、ふつうの夏日（体感26〜31℃）で帯が終日オレンジになり、 判定は A のまま——という状態になりました。判定に暑い側の基準が無いのが理由です。 いまは熱中症警戒アラート（暑さ指数 WBGT 33）のあたりまで無彩色にしてあります。 暑さの警告そのものは、まだ作っていません。

2. 風だけ、少し特別なことをしています

ふつうの天気予報が出す風速は地上10mの風です。これを山の判定に使うと、実際とかなりずれます。

きっかけは利用者からの報告でした。ある日の皇海山（2,144m）を、他のサービスは C、 こちらは終日 A と判定していたのです。実際に数値を引き直すと、原因ははっきりしていました。

どの高さの風かその時刻の値
地上10m（当時、判定に使っていた値）2.73 m/s
850hPa（約1,460m）4.47 m/s
800hPa（約1,950m・山頂に近い）21.02 m/s
700hPa（約3,010m）28.86 m/s

そこで山頂の標高にいちばん近い気圧面の風を判定に使うようにしました。 山頂の標高は国土地理院の標高データから読みます。窓の下に @1950m のように、どの高さの風で判定したかが出ます。

この仕組みには続きがあります。当初は「山頂がモデルの地形より十分高いときだけ気圧面を使う」という 安全弁を付けていたのですが、データ提供側の仕様が変わり、 110峰のうち109峰がその弁に引っかかって、黙って地上10mの風に落ちていました。 ランキングでは C なのに詳細画面では A、という食い違いも起きていました。いまは安全弁を外し、 見るのは山頂の標高だけにしてあります。

3. データはどこから来ているか

すべて公開されている情報源です。独自の観測や独自の予報計算はしていません。

何をどこから
気象データ全般
気温・体感・降水・降雪・風・気圧・雲量		 Open-Meteo Forecast API
モデルは 気象庁（JMA）の jma_seamless。1時間ごと、実績3日＋予報9日
突風・気圧面ごとの雲量 同 Open-Meteo（JMAが返さない項目なので、モデル指定なしの補助リクエスト）
山頂の標高 国土地理院 標高タイル（判定の入力に使います）
地図 国土地理院（標準・淡色・写真・陰影起伏・傾斜量・CS立体図ほか） / OpenStreetMap / Esri / エコリス地図タイル
雨雲・ひまわり・アメダス・天気図 気象庁
地名の検索 国土地理院 地名検索 / Nominatim（OpenStreetMap）

風速は m/s を明示して取得しています。Open-Meteo の既定は km/h で、 かつて取り違えたまま判定に流し、表示が約3.6倍・判定が約3.6倍厳しくなる事故を出しました。 そのとき「判定が厳しすぎる」と誤診して閾値を緩める対症療法まで踏んでおり、 いまは単位の指定が抜けていないかをテストで見張っています。

4. どういう経緯でこの作りになったか

大きな判断は記録として残してあります（ADR）。かいつまむと次のとおりです。

決めたことなぜ
HTML 1ファイルで作る
ビルド工程なし		 置いたファイルがそのまま本番になるので、「手元では動くのに公開すると壊れる」層が存在しない。 実機（iPhone）で踏む不具合が多い作りなので、ソースと配信物が1対1であることの価値が大きい
グラフは uPlot
同梱して使う		 241時間ぶん×4枚を指の動きに追従させたい。軸と座標変換だけ借りて、 昼夜の陰影・雲・天気記号は自前で描いている。CDN は落ちた実績があるのでファイルを同梱
天気記号は自前で描く 絵文字は端末ごとに絵が変わる。判断に使う記号が端末で違うのは困る
公開は GitHub Pages もとは Netlify だったが、無料枠が切れて配信が止まった。 静的ファイルしか無いので、費用も止まる理由も無い方へ移した
判定の風は山頂の高さ 上の「2.」のとおり。地上10mの風では山の風を表せない
気圧配置レイヤーは外した 高低気圧と等圧線を地図に描いたが、格子点APIから作る方式では 日本列島全体を見渡せるほど縮小すると重すぎ、軽くすると粗すぎた。 「実用に耐えない」と判断して撤去した（作ったものを消した記録として残してある）

ふだんの開発では、新しい検査を書くたびに、わざとコードを壊して その検査がちゃんと落ちることを確かめるようにしています。 通り続けるテストは、直したことの証拠にならないためです。
