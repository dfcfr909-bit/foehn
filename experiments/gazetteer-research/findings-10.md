この試行から言えること:

- 検査（案 c）は「同じ名前（山頂名）なのに 300m 以上離れている」「別の山頂名なのに 50m 以内」の2つを出せば、くじゅう型を拾える見込み

| ファイル | 中身 | 変えるときの確認 |
|---|---|---|

- 生成は `scripts/` のスクリプトで行い、手で編集しない（既存の `buildSpots.mjs` と同じ形）

## 3. レコードの形（`gazetteer.json`）

**山域は層にしない**（推奨）。山域は `areas.json` にしか無く、検索では表示用のラベル（`area`）で足りる。層は **山群** と **峰** の2つ（1003山の「総称＜山頂＞」と同じ形）。

### 3-1. 山群（`kind: "group"`）

```json
{ "id": "g:nasudake", "kind": "group", "name": "那須岳", "kana": "なすだけ",
  "rep": "p:1003-249", "members": ["p:1003-249"], "pref": ["栃木県"],
  "src": "gsi1003" }
```

- **座標を持たない**（総称の点は峰から 0.5〜1km ずれ、そこで天気を取ると低い層の風になる → `findings-06.md`）。地図の範囲は `members` の峰から作る
- `rep`（代表ピーク）＝1003山の枝番 `-1`（D-2 で決定。34山中 33山で最高峰。例外は雲仙岳＝普賢岳）
- `members` は**初版では 1003山の山頂だけ**。注記の峰を足すときに、所属の決め方（範囲で自動／手で）を決める

### 3-2. 峰（`kind: "peak"`）

```json
{ "id": "p:1003-249", "kind": "peak", "name": "茶臼岳", "kana": "ちゃうすだけ",
  "group": "g:nasudake", "lat": 37.124861, "lon": 139.963135,
  "elev": 1915, "elevSrc": "標高点", "pos": "summit", "pref": ["栃木県"],
  "areasRef": "nasu/茶臼岳", "src": "gsi1003" }
```

| 項目 | 中身 | 決めどころ・推奨 |
|---|---|---|
| `id` | 自前の ID | 1003山の索引番号を**そのまま使わない**（版で番号がずれると、履歴が別の山を指す）。案では `p:1003-249` と書いたが、**番号に依存しない ID を別に振る**のが推奨（例: 初回生成時の連番を固定して持ち回る） |
| `name` | 山頂名（＜＞の中身。無ければ山名） | 例 `那須岳＜茶臼岳＞` → `茶臼岳`、`巻機山` → `巻機山` |
| `kana` | 読み（ひらがな） | 1003山の読みの＜＞の中。別の読み（丸括弧）は `kanaAlt` に分ける |
| `group` | 山群の `id` | 1003山で＜＞がある行だけ |
| `lat`・`lon` | JGD2011 | GeoJSON の `geometry` の値（桁が多い方） |
| `elev`・`elevSrc` | 標高と種類（三角点・標高点・測定点／`dem`） | 注記だけの峰は `elev` を持たない。DEM で補うなら `elevSrc: "dem"` と明示 |
| `pos` | 座標の確かさ。`summit`（1003山の最高地点）／`label`（注記の文字の位置）／`snapped`（DEM で山頂に寄せた） | **1件ごとの格付けではなく、項目ごとの出典**で持つ（推奨）。途中の状態（寄せた）を表せる |
| `pref` | 都道府県（1〜3） | 1003山の値。D-4 の併記に使う |
| `areasRef` | `areas.json` の峰への参照（重なる場合だけ） | 1-1 の閾値で生成時に付ける。付いた峰は表示に `areas.json` の値を使う |
| `src` | 出典 | 出典表示と、ODbL を混ぜていないことの検査に使う |

### 3-3. 地形名（`kind: "landform"`、注記を足す段から）

尾根・峠など。A で「地形名」の別種別に決定。**注記の 312 から名前で振り分ける**ことになるが、名前の末尾で機械的に切ると「〜ノ頭」（多くは小ピーク）を誤る。
推奨: 名前の規則（尾根・曽根・峠・乗越・首・沢・谷）で自動に分け、**例外は手で持つ表**（`data/gazetteer_overrides.json` のような別ファイル）で直す。

### 3-4. 地名・住所

**同梱しない**（オンライン時に Nominatim・住所検索 API から取るだけ）。`kind` は画面の表示側でだけ持ち、データファイルには入れない（推奨）。

## 4. 検索の流れ（案）

1. 入力を `normalizeSearchName`（既存）で揃え、さらに**ひらがな同士**でも比べる（`kana`）
2. 同梱の `gazetteer.json`＋検索の履歴から、入力中に候補を出す（C で決定）
3. Enter／「検索」で、これまでどおり Nominatim・住所検索 API も呼ぶ（オンライン時）
4. 座標の形の入力なら、名前の検索より先に座標として読む（B で決定）
5. 候補の表記: 峰は「茶臼岳（那須岳・栃木県・1,915m）」、山群は「那須岳（山群）」（D-3・D-4 で決定）
6. 山群を選んだら代表ピークへ移り、構成ピークを並べる（D-1 で決定）

- 検索の履歴の形（名前＋緯度経度＋標高、`sotoki_search_hist`）は**変えない**。`gazetteer.json` の `id` を履歴に足すかは、ID の振り方が固まってから
