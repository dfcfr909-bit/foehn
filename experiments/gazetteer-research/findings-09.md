# 地名・山名検索の調査 09：次フェーズの前に人間が判断すべき点

データモデルを確定する前に決める必要がある点。各項目に、判断の根拠になる一次情報の場所を付けた。
（「推奨」は調査した側の意見で、決定ではない）

## A. 検索窓の範囲

### A-1. 候補に出す種別の範囲 【必須】

選択肢（組み合わせ可）:
山群（総称）／山（ピーク）／峠・尾根など山の地形名／山小屋／登山口／地名（集落など）／住所／施設

- 根拠
  - 地理院の注記分類コードは 311＝山の総称／312＝山、岳、峰等／313＝尖峰、丘、塚等／332＝…峠、坂等／333＝山脈、山地 を分けている（旧形式の 312 には尾根・峠も混ざっていた） → `findings-03.md` 2-1、`raw/gsi_optbv_annocodes_excerpt.txt`、`raw/gsi_vt_labels_311_312.tsv`
  - 山小屋・登山口は、今回の情報源のどれにも**まとまった形では無かった**（住所検索 API に「赤岳天望荘」などが散発的にあるだけ） → `findings-05.md`、`findings-08.md` 表1
  - スーパー地形は施設（コンビニ）まで出す → `findings-08.md` 表1（K3）
- 決めること: 312 に混ざる「尾根・峠・ノ頭」を山と同じ扱いで出すか、別の種別にするか
- 推奨: 初版は **山群・山・地名（＋住所はオンライン時のみ）**。山小屋・登山口は情報源が無いので後回し

### A-2. 座標入力の対応書式の範囲 【必須】

選択肢: 十進度／度分秒／度・十進分（DDM）／UTM／MGRS

- 根拠
  - スーパー地形は 十進度・度分秒・UTM・MGRS（区切りは独自：スラッシュ・ドット） → `findings-08.md` 表5（K1）
  - 地理院地図は 十進度（スペース・カンマ）・度分秒（「度分秒」の漢字）・UTMポイント（MGRS 形式） → 同（G1・G2）
  - 本体は既に6形式を**表示**している（DD・DDM・DMS・度分秒・UTM・MGRS）。表示したものを貼り戻せないと不整合になる → `findings-08.md`「参考」、`docs/spec/map.md`
- 決めること
  1. どの書式まで受けるか
  2. 区切りの方言をどこまで吸収するか（スーパー地形の `35.123/135.951`・`35.12.34/135.59.59` まで受けるか）
  3. UTM の「S」「N」を緯度帯と読むか半球と読むか（→ `findings-07.md`「S」「N」の取り違え）
  4. 経度・緯度の順で打たれた入力（`139.96, 37.12`）を値の範囲から入れ替えるか
- 推奨: **本体が表示する6形式は全部受ける**（コピーして貼れることを保証する）。区切りの方言は数字の並びで読む

### A-3. 入力中に候補を出すか

- 根拠: スーパー地形・地理院地図とも、入力中の候補の有無は**一次情報で確認できなかった** → `findings-08.md` 表2
- 決めること: 候補を出すなら**端末内のデータで出す**しかない（入力ごとに地理院・OSM を叩くと、Nominatim の頻度の制約と山の電波に合わない）。
  → 端末に持つデータの量（B-1）と一体で決める

## B. データの持ち方

### B-1. オフラインで引ける範囲（端末に持つデータの量）

- 根拠: 山で使うためオフライン重視（依頼文）。スーパー地形は地名データを内蔵（K2「山名25000件以上」） → `findings-08.md` 表7
- 決めること: 全国の山名（数万件）を同梱するか、山域ごとに分けて取るか、既存の `areas.json`（110峰）＋履歴だけにするか

### B-2. 読みの情報源

- 根拠: 読みが揃っているのは**地理院ベクトルタイルの旧形式 `experimental_bvmap` の注記だけ**（欠け 0/112）。
  現行形式 `optimal_bvmap-v1` には読みが無い。OSM 22%・Wikidata 6% → `findings-03.md`
- 決めること
  1. 旧形式の注記から読みを取る方針でよいか（**旧形式がいつまで配信・更新されるかは未確認**。現行形式は PMTiles に移り、ファイル配信版は「公開を停止する予定」と告知されている＝`findings-03.md` 2-1。読みを取るなら**早めに一度取り切って手元に持つ**ことになる）
  2. タイルを全国分なめて事前計算する場合の、地理院のサーバ負荷への配慮（地理院地図の利用規約に「負荷をサーバに与える通信に対して、予告なくアクセスの遮断」→ `findings-04.md` 2）
  3. 地理院への問い合わせ（既に問い合わせ済みの件）に、この使い方を含めるか

### B-3. OSM を成果物に混ぜるか

- 根拠: 読みを JSON に写して配信すると ODbL の派生データベースと読める（ODbL §1.0・§4.4 b）。照合だけなら避けられる見込みだが、OSMF のガイドラインは未確認 → `findings-04.md` 1
- 決めること: (a) 混ぜない（照合だけ）／(b) 別ファイルに分けて ODbL で配る／(c) 混ぜて全体を ODbL にする
- 推奨: (a)。地理院の注記で読みが揃うなら OSM の読みは要らない

### B-4. 測量法の扱い

- 根拠: ベクトルタイルは「基本測量成果ではありません」と地理院が書いている。一方、同種アプリは地名データの内蔵に複製承認を取った例がある（当時の数値地図25000） → `findings-04.md` 3
- 決めること: 事前計算した JSON の配信について、地理院の確認を待つか、承認不要と判断して進めるか。
  **条文・地理院の申請案内は今回読めていない**

## C. 山群とピーク

### C-1. 山群の代表ピーク（＝天気の取得地点）を誰が決めるか

- 根拠: **地理院の 1003山は 那須岳＜茶臼岳＞・高原山＜釈迦ヶ岳＞・八甲田山＜大岳＞（＋高田大岳）と山頂を決めている**（→ `findings-02.md`）。一方 Wikidata は那須岳の標高を三本槍岳の値にしている。
  高原山・八甲田山の総称の点は峰から 0.5〜1km 離れている → `findings-06.md`
- 決めること
  1. 代表ピークを **1003山の山頂（那須岳→茶臼岳）に従う**か、**最高峰（那須岳→三本槍岳）**にするか。推奨：1003山に従う（地理院の定義で、根拠を説明できる）
  2. 山群を選んだとき、代表ピーク1点の天気を出すか、構成ピークを並べるか
- 1003山は「主な山頂」だけなので、**構成ピークの全体**（那須岳の三本槍岳など）は気象庁・産総研の一次情報が要る（未確認）

### C-2. 「那須岳」の打鍵で何を出すか

- 根拠: 「那須岳」は総称（地理院の注記 311、OSM の volcano、Wikidata）としても、茶臼岳の山頂（1003山 `那須岳＜茶臼岳＞`・地理院の住所検索）としても入っている → `findings-06.md`
- 決めること: 候補に「那須岳（山群）」と「茶臼岳（那須岳）」の両方を出すか、山群だけにするか

### C-3. 312 のうち尾根・峠を3層のどこに置くか

- 根拠: 312 に「熊見曽根」「中の大倉尾根」「牛ヶ首」「雲谷峠」が混ざる → `raw/gsi_vt_labels_311_312.tsv`
- 決めること: ピークとして扱う／別種別（地形名）にする／出さない
