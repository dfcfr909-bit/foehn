### (1) 何を事前計算するか

| 案 | 長所 | 短所・未確認 |
|---|---|---|
| **尾根だけ** | A 判定の柱（連続性・頑健さ）だけを取り込める。容量が小さい（上表の約半分）。沢の階層の決め方（未解決）を持ち込まない | 沢は端末の `terrainFlow` のまま（10m 格子では細切れ・findings6）。尾根と沢の出所が別になる |
| **尾根＋沢** | 沢の精度も上がる（findings7：+16〜31pt） | 沢の階層（下の(3)）と水面マスク（(4)）が要る。30m の再現は小差 |
| **鞍部は端末の `terrainFindCols` のまま** | findings5 の結論どおり（差が無く、候補数が 2.5〜15倍少ない）。風の補正（3b・3c）の依存が変わらない | 事前計算の尾根と、端末の鞍部の位置がずれうる。落差30m以上の鞍部の100m以内に LANDMARK の尾根がある割合は 92〜94%（findings6） |

- **［事実］** `terrainFlow` の結果を使うのは検証用の重ねだけ（2-1）。置き換えても、利用者に見える既定の機能は変わらない。
- 帯（HAND・稜線からの深さ）や `ridgeId` は升目の値で、線を事前計算してもそれらは出ない。端末で `terrainFlow` を残すか、ラスタでも事前計算するかは、用途（2-3 の質問1）による。

### (2) 解像度：30m か 10m か

- **30m**
  - 本番の設計の格子と同じ。計算は10mの約15分の1、容量は約0.6倍。
  - 尾根は解像度で密度が変わらず（2.5→2.5km/km²）、30m と 10m の位置の一致は 94%（findings6）。**尾根だけなら、30m で柱の性質が得られる**［事実：密度・一致率］。
- **10m**
  - 沢の精度・再現の差がはっきり出る（findings7：10m で +25〜32pt）。
  - 計算は D で約260 CPU時間。メモリは1窓約1.7GB［推測］。
- **未確認**：30m の尾根と 10m の尾根のどちらが「正しい」かは、OSM の尾根線が2窓しかなく判断できない（findings6）。

### (3) 沢の階層：A_out の閾値の決め方

- **［事実］** 現行の既定の網と同じ全長にする A_out の下限は、窓ごとに大きく違った（findings7）。
  - 30m：32.8万〜1,458.5万m²（中央値156万）
  - 10m：10.0万〜141.3万m²（中央値33万）
  - 「A_out の閾値1つ」で現行と同じ密度にはならない。
- **［事実］** hso は解像度で大きく変わる（hso≧7 の密度が 30m→10m で3.5倍・findings6）。hso で階層を決めるのは避ける。
- 案
  - **a. 全国で固定の A_out の段**（例：10万・100万・1,000万m²）をレイヤーにする。物理量なので解像度に頑健。地形で密度が変わるのは実際の地形の差として受け入れる。
  - **b. 地域ごとに、現行と同じ密度になる閾値に合わせる。** 見た目は現行に近いが、閾値の意味が場所で変わる。
- **［未確認・重要］窓の境界の問題**：A_out（集水面積）は、上流が窓の外にある大きな川で過小になる。A_spread も同じ。
  - タイルに切って計算すると、境界で値が飛ぶ。
  - 流域単位で計算する、または大きな余白を取る必要がある。上の「×1.8」の余白で足りるかは未検証。

### (4) 後処理

- **水面・平坦面のマスク**：LANDMARK の沢は水面を横切る。
  - ［事実］本番の既定の網と同じ長さで、30m 13.5%・10m 8.6%（findings7）。現行は `FLAT_*` で避ける。
  - 案：DEM の平坦面（findings6 の定義）だけで外すか、OSM の水面ポリゴンも使うか。
  - ［事実］OSM は中禅寺湖・蛭沢湖を確認できた。w07 の310m・w08 の平坦面は、OSM に水面が無く未確認。
  - ［未確認］OSM を派生物に使う場合のライセンス（ODbL）上の扱い。
- **線のならし**：`linemerge` → 本番の `VEC` と同じならし（[1,2,1]×4）と間引き（0.25升目）を事前にかけておけば、端末の描画（Catmull–Rom）はそのまま使える［推測］。
  - 格子の階段状は 10m では目立ち、30m では升目が粗い（`out/render/jonen_ridge_compare.png`）。
- **ヒゲ（短い行き止まり）**：LANDMARK の尾根は A_spread≧1e5 でも短い枝を持つ。本番と同じ200m未満の刈り込みを入れるかは未検証。

| **GeoJSON（または独自の座標配列 JSON）を格子で分割**（例：z10 のタイル1枚＝約30km四方ごとに1ファイル） | 普通のファイル。1ファイルが小さい（10m・尾根＋沢で1ファイル数百KB 以下［推測］） | ［事実］今の `sw.js` は、同じオリジンのHTML以外を `sotoki-v2` にキャッシュ優先＋裏で更新で保存する。見たファイルは自然にオフラインに残る。ただし**上限・LRU が無い**ので、タイルと同じ上限管理が要る | 追加のライブラリなしで描ける。今の `terrainDrawLines`（升目の座標の折れ線を Catmull–Rom で描く）の入力に近い形にすれば、描画処理をほぼ流用できる［推測］ |
| **MVT タイル（z/x/y.pbf を多数）** | ファイル数が多い（ピラミッドで数万〜数十万［推測］）。Pages のデプロイ10分に収まるかは［未確認］ | タイルと同じ扱いにできる（上限管理の追加が要る） | ライブラリが要る。［事実］`leaflet.vectorgrid` は npm 最新 1.3.0（2017-08-28）・最終コミット 2025-01-09。`protomaps-leaflet` は 5.1.0（2025-06-18）で、README に「**メンテナンスモード**。新機能は入らない。Leaflet の既存システム向けに限って推奨。それ以外は MapLibre GL JS」。PBF の復号も要る |
| **PMTiles（1ファイル）** | 範囲なら 1GB に収まる（D の10mでピラミッド約280MB［推測］）。ただし **git の1ファイル 100 MiB 制限**を超えるので、コミットせず Actions で生成／取得してデプロイする必要がある。Pages の Range 対応は［未確認］（PMTiles 公式は置き場所に挙げる） | **［事実］Cache API は 206（部分応答）を保存できない。** Service Worker 仕様の `put()` に「innerResponse の status が 206 なら TypeError で拒否」とある（[w3c.github.io/ServiceWorker](https://w3c.github.io/ServiceWorker/)）。Range で読む PMTiles は、今の仕組みではオフラインに残らない。IndexedDB に自前で持つなどが要る。［推測］今の `sw.js` は同じオリジンの Range 要求も「キャッシュ優先＋裏で更新」に通し、`put` が拒否される | `pmtiles`（npm 4.5.0・2026-08-10）＋描画ライブラリ（上の MVT と同じ問題） |

- CLAUDE.md（ADR-0002）の「CDN が403等で失敗した実績があるため `vendor/` に同梱」の方針に従うなら、ライブラリは同梱になる。
- 同じオリジン（Pages）に置く限り、ADR-0008 の「追跡できない配信面を持たない」には触れない。外部のストレージ（R2 など）に置くと、新しい配信面になる。

## 2-3 加藤さんに決めてもらう点

1. **事前計算した尾根（・沢）を何に使うか。** ①風の解析の材料だけ（表示は検証用のまま）、②利用者に見える重ねとして出す、のどちらか。
   - いまは「地図として読む用途には使わない」と記録されている。②なら、この判断を覆すことになる。
   - **おすすめ：①から。** `terrainFlow` の利用先が検証用の重ねだけなので、①なら既定の画面に影響が出ない。
2. **何を事前計算するか**（尾根だけ／尾根＋沢）。
   - **おすすめ：尾根だけ。** A 判定の柱は尾根で、沢は階層の決め方（質問6）と水面マスクが未解決。
3. **鞍部は端末の `terrainFindCols` のまま**でよいか（findings5 の結論を設計上も確定させるか）。
4. **解像度**（30m／10m）。
   - **おすすめ：30m。** 尾根は解像度に頑健（位置一致94%・密度不変）で、計算は約15分の1、容量は約0.6倍。10m の利得が大きいのは沢。
5. **対象範囲**（A 東北＋新潟＋栃木／B 中部山岳／C 両方＋α／D 全国）。まず試す範囲と、最終的な範囲。
   - 容量は 30m ならどれも 1GB に収まる。10m の D は形式を選ぶ（GeoJSON 生は超える）。
6. **沢も入れる場合の階層の決め方**。
   - a：全国固定の A_out の段をレイヤーにする。b：地域ごとに現行と同じ密度に合わせる。
   - **おすすめ：a。** 物理量なので解像度・場所で意味が変わらない。窓ごとの下限の差（30m で約33万〜1,460万m²）は地形の差として受け入れる。
7. **配信形式**（格子で分割した GeoJSON／JSON・MVT タイル・PMTiles）。
   - **おすすめ：格子で分割した JSON。** 理由は次の3つ。
     - PMTiles は Cache API が 206 を保存できず、今の Service Worker ではオフラインに残らない（仕様で確認）。
     - Leaflet 向けの MVT 描画ライブラリは、メンテナンスモード（protomaps-leaflet）か、長く更新の無い版（Leaflet.VectorGrid）。
     - 分割 JSON なら、今の Service Worker と `terrainDrawLines` をほぼ流用できる［推測］。
8. **事前計算をどこで回し、成果物をどこに置くか**（ローカル PC／Actions・リポジトリにコミット／デプロイ時だけ含める）。
9. **地理院の標高タイルの派生物を配信することの手続き**（測量法の申請が要るか）を、誰がどう確かめるか。この調査では確認できなかった。
10. **水面マスクに OSM の水面ポリゴンを使ってよいか**（ライセンスの扱い）。それとも DEM の平坦面の判定だけにするか。
11. **CLAUDE.md の「手元から地理院に到達できない」を、実行環境ごとに書き分けるか。** 利用者の PC と Actions からは届き、クラウド開発環境からは届かない（記録）。今回は変更していない。
12. **依頼文にあった「MVT スキーマ」がどこにあるか。** リポジトリのどのブランチ・文書にも見つからなかった。別の場所（Issue・手元のメモなど）にあれば教えてほしい。
