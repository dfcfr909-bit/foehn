## 1. 大原則 — 情報を3層に分ける

分割の軸は「トピック」ではなく **「変更頻度」と「読まれる頻度」**。

| 層 | ファイル | 読むタイミング | 目標サイズ | 更新頻度 |
|---|---|---|---|---|
| **L0 常時** | `CLAUDE.md` | 自動で毎回 | **120行以内** | 月1回程度 |
| **L1 開始時** | `docs/status.md` | セッション冒頭に必ず | **80行以内** | 毎セッション（上書き） |
| **L2 随時** | `docs/spec/*` `docs/adr/*` `docs/ops/*` | 必要になったときだけ | 制限なし | 変更時 |

**L0 + L1 = 200行以内**。これが「AIが毎回読むべきファイル」の全量。
今は `CLAUDE.md`(44) + `handoff.md`(244) = 288行で、しかも handoff は伸び続ける。

## 3. CLAUDE.md の設計

### 書くもの（AIの判断を変えるものだけ）

- 命名規約・コメント言語
- **禁止事項**（ABC評価ロジックの変更禁止、`wrangler.toml`に秘密を書かない 等）
- **地雷**（風速は `wind_speed_unit=ms` 必須、`destination-out` を使わない 等）
- ファイルマップ（どこに何があるか。1行ずつ）
- よく使うコマンド（テスト実行、アイコン生成）
- **セッション運用ルール**（開始時に `docs/status.md` を読む／終了手順／切り上げ提案）

### 書かないもの

- 変更履歴・バージョン履歴 → `git log` と `docs/decisions.md`
- 仕様の詳細（定数値、ピクセル数） → `docs/spec/*`
- 「なぜそうしたか」の長い説明 → `docs/adr/*`

### CLAUDE.md 骨子案

```markdown
# ナギナビ

バックカントリー気象PWA（単一HTML / GitHub Pages / Open-Meteo JMAモデル / Leaflet）

## セッション運用（最初に読む）
1. `docs/status.md` を読む。これが現状と次の一手。
2. 作業は1セッション1テーマ。終わったら「終了手順」を実行して切り上げる。
3. 終了手順: status.md更新 → decisions/ADR追記 → commit & push → 次回プロンプトを status.md 末尾に書く
4. 以下に当てはまったらClaudeから切り上げを提案すること:
   - PRを1本仕上げた / 話題が変わる / 同じ不具合の修正に2回失敗した / 大量調査の直後

## 禁止・地雷（違反すると壊れる）
- ABC評価ロジック（abcScore / abcScoreInv / judgePoint）は**変更禁止**（移植のみ）
- Open-Meteo は `wind_speed_unit=ms` を**必ず**指定（既定km/h。過去に取り違えて事故）
- 天気記号を `destination-out` で抜かない（下の白座布団ごと消える）
- 秘密は `wrangler secret` で登録。`wrangler.toml` に書かない
- 破壊的変更は実行前に要確認

## 規約
- 命名: camelCase（JS）／コメントは日本語
- 段階ごとにcommit分割。各段階の完了時に動作確認を求める
- 1 Issue = 1 PR = 1 セッション

## ファイルマップ
（略：各1行）

## コマンド
- テスト: `node tests/run-all.js`
- アイコン: `node scripts/gen-icons.mjs`

## 詳しくは
- 現状・未完 → docs/status.md
- 仕様 → docs/spec/
- 設計判断の理由 → docs/adr/ , docs/decisions.md
- 本体の関数索引 → docs/spec/code_map.md（全文読む前に必ずこれ）
```

AIは基本読まない。GitHubのトップに出る顔なので、人間の判断材料を置く。

- ドキュメント目次（`docs/` へのリンク）

## 5. 設計書の分割方法

**軸は「変更頻度」。** トピックで割ると、1ファイル内に「変わらない要件」と「毎週変わる実装値」が混ざり、AIがどちらを信じるべきか分からなくなる。

| 種別 | 書き方 | 更新方法 |
|---|---|---|
| 要件（requirements/） | 「〜したい」「〜であること」 | **凍結**。完了したら追記しない |
| 仕様（spec/） | **現在形のみ**。「〜になっている」 | **上書き**。履歴を残さない（gitが持つ） |
| 判断（adr/） | 「〜を選んだ。理由は〜」 | **不変**。覆すときは新ADRを書き旧を Superseded |
| 現状（status.md） | 箇条書き | **毎回上書き** |

分割サイン: **1ファイルが300行を超えたら分割**。
`spec/` の1ファイルは「AIが1回のタスクで読み切る単位」＝150〜250行が理想。

### `spec/code_map.md` — 効果が一番大きい提案

`sotoki_v4.html` は3,400行。AIに全文を読ませると、それだけで巨大な消費になる。
代わりに **関数索引**を置き、AIはここを見て `grep` / 部分読みで飛ぶ。

```markdown
| 関数 | 役割 | 目安行 |
|---|---|---|
| abcScore / abcScoreInv / judgePoint | ABC評価（変更禁止） | 約 400-470 |
| drawWeatherGlyph | 天気記号のベクター描画 | 約 1850-1990 |
| moonPhase / wxMoon | 月齢と満ち欠け描画 | 約 1990-2060 |
| paintNightOverlay / softGradient | 夜帯シェーディング | 約 2100-2180 |
```

行番号はズレるので **±50行の目安**と割り切る。ズレたら関数名でgrepすればよい。
これだけで「本体を読ませる」コストが1/10以下になる。

## 6. Decision Log と ADR の使い分け

### なぜAI開発でこれが効くか

AIは「なぜそうなっているか」を知らないと、**善意で壊す**。
実例が既にリポジトリにある：絵文字→自前ベクター、`destination-out` 不使用、風速単位。
これらは全部「一度やって失敗した」記録。ADRはAIに対する**再発防止装置**として機能する。

### 使い分け

| | ADR (`docs/adr/`) | Decision Log (`docs/decisions.md`) |
|---|---|---|
| 対象 | 構造的・後戻りが高くつく判断 | 軽い判断・調整値の決定 |
| 例 | 単一HTML維持 / uPlot採用 / Pages移行 / 描画方式 | 「凡例を下段に移した」「FAV_R=82に調整」 |
| 粒度 | 1判断1ファイル | 1判断1行 |
| 変更 | 不変。覆すなら新ADR＋ Superseded | 追記のみ |
| 目安 | 年に3〜10本 | 週に1〜3行 |

**判定基準：「半年後に『なんでこうなってるの？』と聞かれるか？」→ Yes なら ADR。**

### ADR テンプレート（`docs/adr/template.md`）

```markdown
# ADR-0000: タイトル

- ステータス: 採用 | 却下 | 置換済み（→ ADR-XXXX）
- 日付: YYYY-MM-DD

## 背景
何が問題だったか。制約は何か。

## 決定
何をどうすると決めたか。1〜3文。

## 理由 / 検討した代案
なぜ他ではなくこれか。**却下した案とその理由を必ず書く**（AIが再提案してくるのを防ぐ）。

## 影響
これにより何が縛られるか。何をやってはいけなくなるか。
```

「却下した案とその理由」欄が最重要。ここが空だと、AIは半年後に同じ案を「改善」として持ち出す。

### Decision Log の形式（追記のみ）

```markdown
## 2026-08
- 2026-08-07 凡例をチャート下段へ移動。ヘッダー1行48pxを死守するため。
- 2026-08-05 FAV_R=82 / FAV_ANGLE=52 に調整。実機で親指の届く範囲を確認。
```

年ごとにファイルを割る（`decisions.md` → 肥大したら `decisions/2026.md`）。

## 7. Issue 管理

### 方針: GitHub Issues を使う。ただし極力軽く。

いまPRだけで回っているが、長期では「次に何をやるか」の置き場が要る。
`status.md` に全部書くと L1 が肥大するので、**未来のタスクはIssueへ逃がす**。

### ラベルは4つだけ

`bug` / `feature` / `chore` / `needs-decision`

（`needs-decision` = 人間が決めないと進めないもの。AIはここで止まる、と決めておく）

### Issue テンプレ（`.github/ISSUE_TEMPLATE/task.md`）

AIに渡す前提なので、**受け入れ条件を必須にする**。

```markdown
## やること
（1文）

## 背景 / なぜ
（任意）

## 受け入れ条件
- [ ] 
- [ ] `node tests/run-all.js` が通る
- [ ] 実機（iPhone Safari）で確認

## 触る予定のファイル
- 

## 触ってはいけないもの
- ABC評価ロジック / （その他）
```

### 運用ルール

- **1 Issue = 1 PR = 1 セッション**。これを超えるIssueは分割する
- ブランチ名に番号: `claude/44-legend-position`
- コミット末尾に `Refs #44`、PR本文に `Closes #44`
- Issueは**セッション開始時に人間が1本選んでAIに渡す**。AIにIssue一覧を漁らせない（コンテキストの無駄）

## 8. TODO 管理 — 3層に分ける

| 期間 | 置き場 | 誰が管理 |
|---|---|---|
| 今このセッション内 | **Claude Code内蔵のTODO機能** | AI（ファイルに書かない） |
| 数日〜数週間 | **GitHub Issues** | 人間 |
| いつか / 要確認 | `docs/status.md` の「未完・要確認」表 | 両方 |

- 現 `handoff.md` の「未完・要確認」表は**そのまま status.md へ**。形式は優秀なので変えない
- コード内の `// TODO` は**Issue番号必須**（`// TODO(#44): ...`）。番号なしTODOは禁止
- 「未完・要確認」が10行を超えたら、Issue化して減らす（status.md を80行以内に保つため）

## 9. Git コミット運用

現行のPRベース運用は良いので、規格だけ足す。

### コミットメッセージ

日本語のまま、先頭にprefixを付ける（既に `worker:` 等を使っているので自然な拡張）。

```
feat: 凡例をチャート下段へ移動
fix: 風速の単位取り違えを修正（km/hをm/sとして扱っていた）
docs: 引き継ぎメモを status.md に分割
refactor: 天気記号の描画を drawWeatherGlyph に集約
chore: uPlotを1.6.32に更新
test: スクラバーのスモークテストを追加
```

prefixがあると `git log --oneline --grep='^fix'` で事故履歴だけ追える。

### 粒度

CLAUDE.md の「段階ごとにcommit分割」を維持。基準は **「ここで止めてもアプリが壊れていない単位」**。

### タグ（新規提案・単一HTML構成なので効果大）

リリースごとに `git tag v4.42.0`。単一HTMLなので、
**タグさえあればいつでも「あの時動いていた版」を1ファイルで取り出せる**。
現状バージョンは HTML 内にしかないので、タグを打つ運用にする価値が高い。

### ブランチ

- `main` 保護（直push禁止、PR経由必須）
- 作業: `claude/<issue番号>-<短い英語>`
- **マージ済みブランチは使い回さず `git checkout -B <branch> origin/main` で作り直す**
  - ただし**このルールは「main が実態である」ことが前提**。2026-08-07 に main が42コミット
    遅れた状態でこの手順を実行し、衛星機能が存在しないコードを読んで誤答する事故が起きた。
    前提が崩れたときに事故を起こす手順なので、**機械的なチェックとセットで運用する**
    （`.claude/hooks/session-start.sh`。第13節参照）

## 10. セッションを切り替えるタイミング ★

長期開発では、**構成よりこれの影響が大きい**。

### 切るべきサイン

| # | サイン | 理由 |
|---|---|---|
| 1 | **Issue/PRを1本仕上げて push 済み** | 最も自然な切れ目。ここで切るのが基本 |
| 2 | **話題が変わる**（気象アプリ → KYT、実装 → ドキュメント整理） | 前の文脈が丸ごと無駄になる |
| 3 | **大量の調査・grep の直後、実装に入る前** | 調査ログが実装の邪魔をする。結論だけ status に書いて切る |
| 4 | **同じ不具合を2回直して2回とも外した** | ★最重要。文脈が汚染されている。粘るほど悪化する |
| 5 | **AIが同じ提案を繰り返し始めた／前の指示を忘れ始めた** | 劣化の初期兆候 |
| 6 | コンテキスト消費が 60〜70% を超えた | 経験則の閾値 |

### `/compact` より新セッション

`/compact` は要約なので**必ず情報が落ちる**。しかもどれが落ちたか分からない。
一方 `status.md` は自分で書いた要約なので、**何を残したか分かっている**。
→ **原則: compactせず、status.md を書いて新セッション。**

### セッション終了手順（毎回これをやる）

1. `docs/status.md` を上書き更新（現状 / 未完 / 次の一手）
2. 判断があれば `docs/decisions.md` に1行、構造的なら ADR を1本
3. `node tests/run-all.js` → commit → push → PR
4. **`status.md` の末尾に「次セッションの最初のプロンプト」を書く** ← 効果が非常に大きい

```markdown
## 次セッションの最初のプロンプト
> docs/status.md を読んだうえで、Issue #45（気圧パネルの警告帯が
> 24時間境界をまたぐと消える）を直して。再現手順は Issue 本文にある。
> `sotoki_v4.html` の paintPressureWarn 付近だけ見れば足りるはず。
```

これがあると、次のセッションは**探索ゼロで実装から始められる**。

### Claude 側からの切り上げ提案

CLAUDE.md に明記して、AIから言わせる：

> 上記の切るべきサイン 1〜6 に当てはまったら、作業を続ける前に
> 「ここで切り上げて別セッションに移行することを勧めます。理由は〜。
> 終了手順を実行しますか？」と提案すること。

## 12. コンテキストを肥大化させない運用

1. **本体を全文読ませない** → `docs/spec/code_map.md` で関数索引を引き、grep/部分読みで飛ぶ（第5節）

## 13. `.claude/` の活用（追加提案）

### 実装済み: `.claude/hooks/session-start.sh`（ブランチ鮮度ガード）

2026-08-07 の事故（`main` が42コミット遅れた状態でセッションが始まり、存在しない
はずの衛星機能について2回誤答した）を受けて追加。セッション開始時に `git fetch` し、

- 現在ブランチが `origin/main` より遅れていたら警告
- `origin/main` より10コミット以上先行し、**かつ main より新しい**ブランチがあれば
  「main が実態から遅れている可能性」を警告（main 自体の陳腐化を検出する逆方向チェック）

を出力する。作業ツリーの版数（`app-version`）も併せて表示する。

**設計の要点は「規約ではなく機械にする」こと。**
事故の直後は「CLAUDE.md の『まず handoff.md を読む』を守れば防げた」と総括されたが、
これは誤り。**ドキュメントはブランチ状態の一部**なので、古いブランチに入った瞬間に
`CLAUDE.md` も `handoff.md` も一緒に古くなる。実際、当時の `main` の handoff.md には
「バージョン: v4.42.0」と書かれており、読んでも34バージョン古い現状を教えられるだけだった。

> **ブランチ状態のズレは、そのブランチの中にあるドキュメントでは防げない。**
> 防げるのは、ブランチの外側で動く仕組み（フック）だけ。

### 今後の候補

現在は statusline とこのフックのみ。以下を足すと運用が回りやすくなる。

- **カスタムスラッシュコマンド**
  - `/session-close` … 第10節の終了手順を1コマンドで実行
  - `/session-start` … status.md を読んで現状を要約し、次の一手を提示
- **settings.json の permissions** … `node tests/run-all.js`、`git log`、`git diff` などを事前許可し、確認プロンプトを削減
- **hooks** … commit 前に `node tests/run-all.js` を自動実行（テスト忘れの防止）

## 14. 導入ロードマップ

一気にやらず、**1段階1PR・1セッション**で。

| 段階 | 内容 | 効果 |
|---|---|---|
| **1** | `docs/status.md` を新設（handoff.md の「現状」「未完」を移す）＋ `handoff.md` を `docs/archive/` へ退避＋CLAUDE.md の導線を差し替え | **即効性最大。** 毎回の読み込み量が 288行 → 130行に |
| **2** | `docs/adr/` と `docs/decisions.md` を新設。「重要な経緯」から ADR 4〜5本を切り出す | 再発防止。「善意で壊す」が止まる |
| **3** | `README.md` を書く（人間向け＋免責） | GitHub の顔。AI効率には無関係だが必要 |
| **4** | `docs/spec/` に仕様を分割、`code_map.md` を作る | 本体全文読みが不要になる |
| **5** | Issue テンプレ・ラベル・コミットprefix・タグ運用を開始 | 運用の定着 |
| **6** | `.claude/` にスラッシュコマンドと permissions | 手数削減 |

段階1と2だけでも、体感の8割は取れる。

## 15. まとめ（この提案の要点3つ）

1. **`handoff.md` を「毎回読む status.md（80行）」と「必要時に読む spec/adr」に割る。** 毎回の読み込み量を固定化するのが全ての土台。
2. **「重要な経緯」を ADR に昇格させ、却下した案とその理由を明記する。** AIが半年後に同じ失敗を提案してくるのを構造的に防ぐ。
3. **セッションは PR 1本ごとに切る。切る前に status.md と「次の最初のプロンプト」を必ず書く。** `/compact` に頼らない。
