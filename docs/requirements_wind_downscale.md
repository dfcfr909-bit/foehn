# 要件定義書（案）: 風の強さの細分化レイヤー（WindNinja の表を端末で読む）

**状態: 案（2026-10-16）。利用者の承認待ち。**

## 背景

- 「尾根と沢の細かい地形で風の流れを細かく見たい」（利用者・2026-10-15）
- 調査は `experiments/windninja/README.md`（findings-01〜04）。決まったこと：
  - WindNinja の**質量保存の解法**で、山域ごとに 8方位の「倍率と向きの曲がり」の表を Actions で前もって作る（升目 60m・一辺 32km）
  - 予報の風との合わせ方は **案A（山頂基準）**：その地点の風 ＝ 判定の風 × 倍率(地点) ÷ **倍率(基準の峰)**
    - 基準の峰＝**選択地点にいちばん近い、表の範囲内の峰**（`areas.json` の峰。表の JSON の `peakRatio` を風向で按分）。
      ⚠ 選択地点そのものの倍率で割らない（選択地点が谷なら谷の小さい倍率で割ることになり、峰で判定の風と一致しなくなる）
    - 判定の風は選択地点の標高の気圧面の風（ADR-0006/0011）。選択地点が峰でないとき、峰の高さの風とは違う。
      **選択地点の標高が基準の峰より 300m 以上低ければ**凡例に「選択地点が峰より低い：峰の風は予報より強い見込み」と添える（塗りは出す）
    - **基準の峰の倍率が 0.3 未満**（風がほぼ止まる升目に峰が乗った）なら塗らない（割り算で全体が膨らむ）
    - 判定の風が**地上10m風に落ちた時刻**（`windTrace.kind === 'ground'`。山頂が最下層より低い・標高不明）と**風が欠けた時刻**（`windMissing`）は塗らない。
      理由を凡例に出す（地上10m風は峰の高さの風ではないので、案Aの前提が崩れる）
  - ⚠ この解法は**風下の陰を出さない**（風を逆向きにしても倍率が同じ）。陰は v4.177.0 の「風の当たり方」で見る（利用者の決定 A）
  - 運動量の解法（OpenFOAM）は急な山で発散して使えなかった（findings-04）

## 何を出すか

- 地図の気象の区分に「風の強さ（地形）」を足す。**選択地点・選択時刻の判定の風**（`state.allData[i]` の `wind`・`wdir`）を、**選択地点に近い峰（基準の峰）で判定の風と一致するように**、表の倍率で地図の各点へ配る
  - 色＝推定の風速（m/s）。色の段は「風の流れ」の背景（`WIND_FLOW.COLORS`）と同じにする（同じ m/s が同じ色）
  - 向きは表の曲がりを足した向き（矢印の有無は決めること #1）
- 風向は判定の風の向き。8方位の表のうち、挟む2方位を角度で按分（findings-02：45° 離れていても差は中央 0.04）
- 押すと札：その点の推定の風速・倍率（基準の峰に対して・峰の名前も出す）・使った風・表の出どころ
- **選択地点が表の範囲の外**なら塗らない（基準の峰が決まらない）。凡例に「この地点は表の範囲外」
- **表の無い山域**では出さない（行に「この山域の表はまだ無い」）

### 画面と about に必ず書くこと

- 「**推定**。風下の斜面は強めに出る（風上と同じ倍率になる計算）。陰は『風の当たり方』で見る」
- 「選択地点に近い峰（◯◯山）で判定の風と一致するように合わせた値。谷・樹林の中は強めの見込み」
- 判定（A/B/C）・グラフ・矢印には使わない

## 作り方

- 表：`data/wind/<山域id>.png`（8方位を縦に積む・R＝倍率×64・G＝曲がり×127/180＋128）＋`.json`（範囲・升目・峰の倍率）。
  Actions（`windninja.yml`）で作り、PR で入れる
- 端末：レイヤーを入れたときに選択地点の山域の表を取りに行く（PNG を `createImageBitmap(blob, { colorSpaceConversion: 'none', premultiplyAlpha: 'none' })` で読み、
  Worker で R・G を取り出す。⚠ 色空間の変換を切らないと R・G がずれる見込み・**未確認** → 検査で読み戻す）
- **控えの置き場所（決めること #3 と結びつく）**：いまの `sw.js` は同じサイトのもの（`outlook.json` 以外）をすべて
  「キャッシュ優先＋裏で取り直し」でアプリ本体の控え（`CACHE_NAME`）に入れる（`sw.js` 241〜272行）。`data/wind/*.png` もそこへ入る
  - 案 a. **何も足さない**：控えに上限は無く（表は数個・各 約 2 MB なので量は問題にならない）、**開くたびに裏で約 2 MB を取り直す**。
    `CACHE_VERSION` を上げると消えるので、**更新の直後は圏内で一度開くまで圏外では出ない**
  - 案 b. **`sw.js` で `data/wind/` をタイルの控え（150 MB・LRU・取り直さない）へ回す**：更新でも消えず、通信も減る。⚠ `sw.js` に触れる（確認が要る区分）
  - ⚠ 本体から Cache API や IndexedDB に控えても、`sw.js` が別に二重に控える。控え方は `sw.js` の側で決める

## 決めてほしいこと

| # | 項目 | 案（推奨を先に） | 理由 |
|---|---|---|---|
| 1 | 見せ方 | **色だけ**／色＋向きの矢印（約 300m おき）／「風の流れ」の粒子に組み込む | 色だけが最も軽く誤読しにくい。粒子への組み込みは粒子の補正（遮蔽・コル）と二重になるので後で |
| 2 | 表を作る山域 | **谷川だけで試し、実機で良ければお気に入りの山域から足す**／最初から 51山域 | 1山域 約 2 MB。51山域で約 100 MB を Pages と git の履歴に置くことになる |
| 3 | 端末への控え方 | **a. 何も足さない（sw.js に触れない）**／b. sw.js でタイルの控えへ回す | 試す段では a で足りる（谷川1つ・約 2 MB）。山域を増やす・圏外で困るなら b。お気に入りの山域を前もって取るのは段2「お気に入りごとの DEM 保存」と一緒に |

## 触れること・触れないこと

- 触れない：ABC評価・`areas.json`・判定の風の作り方・粒子の補正
- `sw.js`：案 a なら触れない。案 b なら触れる（確認が要る区分）
- 新しい送信先：無し（表は自分の Pages から取る）。ただし**表示の数字の出どころとして WindNinja が増える**ので「外部の情報源」の区分としてマージ前に確認を取る
- 表を作る道具（`.github/workflows/windninja.yml`・`scripts/windninja/buildWindTable.py`）は PR #237・#238 で入れる（確認が要る区分）。
  表は 8方位（0〜157.5°。逆向きは同じ表）に減らした。段1で、出力先を `experiments/windninja/tables/` から `data/wind/` へ移す
- 出典：「地理院タイル（標高タイル）を加工して作成」「WindNinja（米国農務省林野局）で計算」

## 検査

- 倍率の按分（2方位の間）・逆向きの方位を同じ表で引く・**基準の峰で判定の風と一致する**・範囲外は塗らない・PNG の符号の読み戻し（色空間の変換で R・G がずれない・A=0 の欠けの升目で R・G が壊れない）
- 基準の峰の倍率が 0.3 未満・地上10m風に落ちた時刻・風が欠けた時刻は塗らず理由を出す／選択地点が峰より 300m 以上低いときの注記
