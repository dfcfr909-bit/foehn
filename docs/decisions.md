### 移設分（版数は当該の修正が入った版）

- **時間移動UIは「下部スクラバー帯＋タップ」**（v4.30.0）。「チャート横スワイプ」→「スライダー＋タップ」→現行、と2度変えている。スライダーが使いにくかった原因は**密度**で、73時間を幅約336pxに載せて1時間≒4.6px、指1本が約9時間ぶんに相当していた。帯は1時間=14pxなので指1本が約3時間。**チャート直接スワイプは一度採用して撤回した方式なので、戻すときは慎重に**（現在チャートの横スワイプは `overflow-x: hidden` で無効）。
- **お気に入り円柱のDOMを作り直さない**（v4.30.0で修正）。地点を選ぶたびに `renderFavRotary()` が `innerHTML` を全消しして駒を作り直し→スクロール位置がリセット→再センタリング、の二段構えで引っかかっていた。いまは地点リストの顔ぶれが変わらない限り作り直さない（`favRotaryKey` で判定）。**ここに手を入れるときはDOM再構築を増やさないこと。**
- **選択線の位置を固定値に戻すと末尾の空白が戻る**（v4.31.0で修正）。選択線を画面の14%位置に固定していたため、最後の時刻を選択線へ持ってくるには右に画面幅の86%ぶんの余白が構造的に必要で、それが空白に見えていた。いまは `chartPadL`/`chartPadR`=0 とし、選択線はふだん `SCRUB_POS`(50%) に置いて両端の ramp px ぶんだけ端へ寄せることで、余白ゼロのまま先頭・末尾に届かせている。
- **狭い枠での円柱は「半径」でなく「1駒の角度」を広げる**（`FAV_ANGLE`）。ヘッダーへ移した際に隣の駒が正面の駒に重なった。角度を広げると隣の駒がより外側（x = R sinθ）へ行き、かつ強く圧縮される（幅 ∝ cosθ）ので重なりが解ける。駒は絶対配置なので、**枠外へ出たものは `display:none` にしないとスクロール範囲が狂う**。
- **スクロール追従をイベント頻度に依存させない**（上下の赤線のズレ。原因3つを段階的に潰した）。①選択線の更新を `requestAnimationFrame` に逃がして1フレーム遅れた ②なぞり終わりの吸い付きが smooth で帯の慣性と競合した（以上 v4.33.0） ③**本命**＝追従を scroll イベントに載せていた。帯はコンポジタ側で滑らかに動くのに対し scroll イベントは間引かれるため、JSで動かす側だけが遅れる（v4.34.0）。**なぞり中は rAF ループで毎フレーム実測し、上下の線は同じ一つの値で置く。吸い付きは即時。**
- **チャートと帯は必ず同時に動かす**（「現在」ボタンで飛ばない件。v4.36.0で修正）。チャートだけを `scrollTo({behavior:'smooth'})` で動かしていたため、ミラーで動いた帯のscrollイベントが「なぞり」と誤検出され、`scrubFrame` が `chartsWrapper.scrollLeft` を書いてアニメーションを打ち切り、元の index へ吸い付いていた（「下のバーは一瞬飛ぶが上が追従せず、下も元に戻る」症状）。**標準の smooth スクロールは片方しか動かせないので使わず、自前rAFの `animateScrollTo()` を使う。**
- **帯とチャートは同じ座標系（余白・px/h・スクロール量・`idxToX()`）を共有させる**（上下の時刻のズレ）。帯の指標を中央50%固定、チャートの選択線を画面の `SCRUB_POS`(14%) に置いていたため両者が別の場所を指し、目盛り間隔も帯14px/h対チャート約13.08px/hで違っていた。**どちらか一方だけの寸法をいじるとまたズレる。**
- **気象庁の `targetTimes` は「古い順」の配列。実況は末尾側から選ぶ**（衛星の雲が実況と大きくずれた件。v4.76.1で修正）。`jmaTimes` が `list.find(t => t.basetime === t.validtime)` で**先頭＝一番古い実況**を拾っていた。同ファイルの `nowcastSeries` は最初から一番新しい実況を選んでおり、**同じ時刻表を2通りに解釈していた**のが根本。両方 `latestObsTime` に寄せてある。テストのスタブが時刻表を**1件しか返していなかった**ため先頭を拾う実装でも通ってしまった → **時刻表を模すスタブは必ず複数件・古い順で返すこと。**
- **衛星の位置ズレで「投影」を再調査しないこと**（2026-08-07 クローズ）。修正前にオーバーレイの外枠がスクショで平行四辺形に歪んで見えたため投影も疑って記録していたが、v4.76.1 の実機確認で雲の位置・降雨レーダーとも実況と一致した。**ズレは時刻起因が全て。** 将来また位置ズレが出たら、まず疑うのは投影ではなく時刻表の選び方。

### 2026-08-09

- **地図の山域レイヤーは「一般的な山地・山脈図」にしない**（#69）。要望は書籍にあるような山脈の色分け図だったが、**そういう図を配信している公式タイルが無い**うえ、あっても**ランキングの山域とはズレて混乱する**。`areas.json` から**評価単位そのもの**を描く方式にしたので、地図と一覧が必ず一致し、判定の色（A/B/C）まで乗せられる。
- **山域の円の中心は「峰の単純な重心」のまま**（#69。標高加重と最高峰中心を却下）。`富士周辺` で富士山が円の南の縁に来る（中心とのズレ11km）のは、同居する三ツ峠山(1,785m)が重心を北へ引くため。検討した代案は2つとも割に合わない: **標高加重**は 11.0→7.1km と効果が小さいうえ全山域の半径が+2%、「標高が高い＝中心」という理屈も薄い。**最高峰中心**は半径合計が**+47%**に膨らみ、石鎚・剣山は 49.5→95km で四国が円で埋まる（半径は最遠の峰まで届く必要があるため、中心を端に寄せると必ず膨らむ）。**歪みの原因は計算式ではなくデータ側**——富士山は独立峰なので本来1座だけの山域が素直。直すなら `areas.json` の分け方を見直すこと。
- **山域レイヤーの色は「ランキングを開いた後」にだけ付ける**（#69）。地図を開いただけで全国110地点ぶんの気象データを引くと通信が重く、Open-Meteoのレート（#14）を悪化させる。`refreshRanking()` が組んだ**あと**に `areaGradeById` を渡す。色がまだ無いことは**パネルに出す**（黙って灰色にしない）。
- **`pickMapPoint` の二重定義に注意**（#69の作業中に発見・修正）。3引数版（名前つきで選ぶ）が、後から宣言された2引数版（長押しのピン）に**関数宣言の巻き上げで上書き**されていた。そのため検索結果をタップしても**名前が捨てられ逆ジオコーディングし直し、`mapFlyTo` も呼ばれず地図が動かなかった**。長押し側を `pickPinPoint` に分離。**同名の関数を後方で再宣言しないこと**（単一HTMLで全部が同じスコープなので起きやすい）。

### 2026-08-14

- **山頂の吸着は「elev に一致する最も近い点」では山頂を指さない**（#13）。
  一致窓は ±MATCH なので、山頂を芯とする円錐では **elev−MATCH の等高線**が
  いちばん外側に広がる。元の座標がずれていると、その等高線のうち手前側の点が
  「最も近い一致点」になり、**山頂の手前・約MATCH m低い肩で止まる**。
  止まる向きは常に元のズレの方向なので、誤差が誤差を呼ぶ。
  実測がそのまま証拠で、要確認12峰の**全部**が `elev−14〜15m` に着地していた
  （平ヶ岳 −15 / 笠ヶ岳 −14 / 常念岳 −14 …）。近傍最高点は公称標高とほぼ一致
  していた（笠ヶ岳2895/2898・西吾妻山2035/2035）ので、**山頂は0.5km以内に
  あったのに手前で止まっていた**。条件を2つにして直した——
  ① elev と一致する ② 周囲0.5kmに自分より高い点が無い（＝峰の芯）。
  ⚠ **同値は許す。** 平らな台地は周囲に自分より高い点が無いのでそれ自体が頂上で、
  弾くとメサ状の山頂を落とす。落とすのは「もっと高い芯を持つ輪」だけ。
  ⚠ Δ（DEMの読み − 公称標高）を出力に足した。**−14〜15m が並んだらこの偏りの再発**。
- **移動距離の小ささを「安全」の根拠にしない**（#13）。旧規則の修正案のうち
  「1km未満だから同一山塊内で安全」として15件を先に入れたが、規則を直して回し直すと
  **越後駒ヶ岳はさらに4.76km動いた**（37.0809 → 37.1236）。先に入れた値は
  旧規則が掴んだ山頂でない点だった。**小さく動いたものほど「もう合っている」ように
  見えるが、偏りは距離と無関係にかかる。**
- **標高だけでは「どの山か」を確かめられない**（#13）。DEMの吸着は同じ標高の別の峰に
  当たっても気づけない。実際 `areas.json` の平ヶ岳の座標は**至仏山の近く**を指しており、
  半径6kmの探索で出た「範囲の最高点2225m」は至仏山(2,228m)の読みだった。
  地理院の地名検索（`scripts/searchPeaks.mjs`）で名前から座標を引いて突き合わせる。
  **標高で「山頂かどうか」、名前で「どの山か」**という分担にする。
  ⚠ 地名検索は**座標の採用には使わない**。代表点は最高地点とは限らず、三角点が山頂と
  一致しない山も多い（富士山の二等三角点と剣ヶ峰）。`elev` は公称の山頂標高なので、
  代表点をそのまま入れると標高と座標が別の場所を指す。
  ⚠ **完全一致で絞ること。** 部分一致だと地名辞書に無い山で住所・施設を拾う
  （飯豊本山→「福島県小野町大字飯豊本飯豊」100km、日光白根山→「日光白根山ロープウェイ」）。
  16件の要確認のうち7件が誤検出で、**本物（大朝日岳13.25km・平ヶ岳6.64km・五竜岳6.41km）が
  その中に埋もれていた。**
- **Actions で回す道具は非TTYでも進捗を出すこと**（#13）。`snapPeaks.mjs` の進捗表示を
  `isTTY` 限定にしていたため、**29分間まったく出力が無かった**。ログはジョブ完了まで
  取れないので、外からは「重い」のか「1本のリクエストで止まった」のか区別できない。
  併せて `fetch` に `AbortSignal.timeout` と再試行を入れた（時限が無いと無言で止まる）。
- **タイルを際限なくキャッシュしない**（#13）。256×256を入れ子のJS配列で持ったまま
  全部残していたら、`--all`（110峰・約4,000枚）で**ヒープ4GBを使い切って落ちた**
  （90/110で OOM）。`Float32Array`（1枚256KB）に持ち替え、400枚で頭打ちにした。
  ⚠ データ無しは **-Infinity**。NaN にすると移動最大値フィルタの比較が常に false になり、
  単調デックから抜けなくなる。
- **ワークフローの選択肢に `on`/`off`・`yes`/`no` を使わない**。YAMLが真偽値として読み、
  許可値の一覧が空になって `workflow_dispatch` が422で弾かれる
  （`Provided value 'on' for input 'all' not in the list of allowed values []`）。
  `changed`/`all` のように真偽値でない語にする。
- **`checkPeaks` の許容差200mは緩すぎた**（#13）。笙ヶ岳（1,635m）は座標が山頂から
  1km以上外れていたのに、指していた斜面が1,518mあったため差は**117m**にとどまり、
  200mの網を抜けて「合格」になっていた。**「全110峰が200m以内」は、山頂を指している
  ことの保証にならない。** 全110峰を60mで洗い直すと要確認は笙ヶ岳のただ1件で、
  正しく山頂に載っている109峰はすべて60m以内だった。既定を**100m**に下げた
  （109峰の60mと笙ヶ岳の117mの間を取った）。
- **一致窓（`--match`）を広げて解決しようとしない**（#13）。笙ヶ岳が見つからないのは
  DEMが尖った山頂を低く読むせいだと考えて30mに広げたら、**Δ+29m の点**を掴んだ。
  DEMは山頂を数m低く読むのであって**高く読むことはない**。つまりそれは公称より
  29m高い別の高まりで、三角点ではなかった（移動0.40kmで、地図上の△1634.9には届いていない）。
  ⚠ **Δが正に振れた修正案は疑うこと。** 窓を広げるのは最後の手段で、広げたら
  必ず地図と突き合わせる。
- **`Δ` の符号が「山頂かどうか」の決め手になる**（#13・笙ヶ岳で確定）。DEMは10mメッシュの
  標本なので山頂を**数m低く**読む。逆に**公称より高く出たら、そこは目的の山頂ではない**。
  笙ヶ岳では一致窓を30mに広げて出た 39.0971,140.0042 が **Δ+29m** で、
  地図で読んだ三角点 39.0927,140.0020（**Δ−2m**）から0.52km離れた別の高まりだった。
  **Δが正の修正案は採らない。**
- **山名の表記揺れに対応する。1字違うだけで検索は空振りする**（#13 の最後の落とし穴）。
  鳥海山の笙ヶ岳は地理院に「笙**ガ**岳」、OSMに「笙**ケ**岳 二峰」で載っている。
  利用者が素直に「笙ヶ岳」と打つと**岐阜県の笙ヶ岳(908m)しか出ず、選ぶと500km先へ飛ぶ**。
  検証スクリプトも同じ理由で空振りし、**「地名辞書に無い＝同名の別の山」と誤って
  結論づけていた**（実際には有り、引けていなかっただけ）。
  - 揺れの組は `ヶ/ケ/ガ/が/ヵ/カ` と `ノ/の/之`。**引くときは揺れを作って複数回引き、
    照合するときは揺れをならしてから比べる**（`nameSearchVariants` / `normalizeName`）
  - ⚠ **引く回数に上限を置く**（3回）。1語で6通り投げると Nominatim の利用条件から外れる
  - ⚠ **並び順が「どれを選ぶか」を決めてしまう。** 同名の山は各地にあるので、
    検索結果は**いま見ている場所に近い順**に並べる。これが無いと、揺れを直しても
    利用者が遠い同名峰を選んでしまう
  - 検査は `tests/smoke_mapsearch.js`。⚠ **スタブは「表記が完全に一致したときだけ返す」
    ように書くこと。** 緩めると、揺れに対応していない実装でも素通りする
- **山名検索の情報源は OSM だけでは足りない。国土地理院を足す**（#13 から派生）。
  OSM(Nominatim)は日本の山名の網羅性が低い。「釈迦ヶ岳」で返るのは山梨の2件だけで、
  **矢板（高原山）の釈迦ヶ岳が出てこない**。⚠ **件数上限の問題ではない**——

  marching squares は辺の上で線形補間するので**頂点はほぼ理想の線の上に乗る**。
  角張って見えるのは頂点の間を直線で結んでいるからで、ズレは弦の中央に出る。
  最初は頂点で測ってしまい、粗い格子でもズレが0.067度しか出ずに検査にならなかった。
- **合成データの中心を格子点のちょうど中間に置かない**（`smoke_pressure`）。
  38/138 のような切りのよい値だと、刻みによっては4点が同着になり、
  どれも「近傍より真に低い」を満たさず**極値が1つも出なくなる**。半端な値にする。
- **計算した気圧配置レイヤーを外した**（#26 / 2026-08-20）→ `docs/adr/0010-pressure-layer-removed.md`。
  429・重さ・角張り・拡大で消える、を順に直しきったうえで、**それでも「実用に耐えない」**
  という評価だった。⚠ **個々の不具合ではなく形が噛み合っていない。**
  大まかな気圧配置には広い範囲が要る → 広い範囲は点数が増える → レートに当たる →
  点数を抑えると升目が300〜900kmになる、という三すくみ。
  ⚠ **補間で見た目は救えたが、情報量は粗い格子のまま**で評価は変わらなかった。
  ⚠ **パラメータの調整で越えられる壁ではない。** 点数の上限を上げる案は
  「利用者の回数を消費するので、こちらの都合で上げてよい数字ではない」として却下。
  次にやるなら①事前に計算して配る（`gen-outlook.mjs` と同じ形。CIで1日数回なら
  格子をずっと細かくできる）②気象庁の天気図を別パネルの1枚絵で出す（前線が読める）。
  ⚠ **地図に重ねるのは投影法が違うので不可**（H の位置が数百kmずれる）。
- **「直しきったが要件を満たさない」ときは、直した記録ごと残して外す**（#26）。
  3回の実機指摘をすべて直したうえでの撤退なので、**何を試して駄目だったか**が
  次の人にとっていちばん価値がある。コードは `6249445` に残っており、
  marching squares・Catmull-Rom 補間・局所極値の判定は**やり方を変えても使える部品**。
- **気象庁の天気図は「別パネルの1枚絵」で出す**（#26 / 2026-08-25）→ `docs/spec/ui.md`。
  ADR-0010 の代替案2を実装した。実測（`scripts/probeJma.mjs`）で分かったこと——
  `list.json` も画像も **`access-control-allow-origin: *`**、**24時間後・48時間後の
  予想天気図まで配信**、日本周辺(600x581)とアジア広域(600x512)の2種類。
  ⚠ **通信は一覧1回＋画像1枚**。格子点APIのような点数の問題が無く、三すくみが解けている。
  ⚠ **前線が描いてある**のが最大の利点。気圧の場だけからは原理的に出せない。
- **ファイル名の時刻はUTC。そのまま出すと9時間ずれる**（天気図）。
  さらに ⚠ **予想図の2つ目の時刻は基準時刻であって対象時刻ではない**（対象は基準＋24h/48h）。
  取り違えると「1日前の予想」と表示してしまい、**絵は正しいので気づけない**。
  `tests/smoke_wxmap.mjs` が両方を数字で固定している（8/25 12:00Z → 8/25 21:00 JST、
  基準 8/25 00:00Z の FSAS24 → 8/26 09:00 JST）。
- **一覧の並び順を仮定しない**（天気図）。昇順で返ってくるように見えても、
  名前から読んだ時刻で最新を選ぶ。順序が変われば**黙って古い絵を出す**ことになる。
- **`display` をインラインの空文字で戻さない**（天気図の画像）。
  CSS 側で `display: none` を指定していると、インラインを空にすると CSS が効いて
  消えたままになる。明示的に `block` を指定する（テストで踏んだ）。
- **調べるときは「中身の形」まで出す**（`scripts/probeJma.mjs`）。
  1回目は出力を先頭300文字で切っていたため、**予想天気図があることに気づけなかった**。
  取れた／取れないだけでなく、**何がどれだけあるか**まで見ないと画面を設計できない。
