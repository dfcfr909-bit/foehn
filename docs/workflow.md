# 開発の進め方（Issue・コミット・ブランチ・タグ）

提案書 `docs/project_structure_proposal.md` 第7〜9節を運用に落としたもの。
**極力軽く。守れない規約は書かない。**

## 1 Issue = 1 PR = 1 セッション

これを超える Issue は**分割する**。

- Issue は**セッション開始時に人間が1本選んで AI に渡す**。
  AI に Issue 一覧を漁らせない（コンテキストの無駄）
- セッションを切る前に `docs/status.md` と「次セッションの最初のプロンプト」を必ず書く

## ラベル（4つだけ）

| ラベル | 意味 |
|---|---|
| `bug` | 動かない・壊れている |
| `feature` | 新しい機能・既存機能の拡張 |
| `chore` | ドキュメント・テスト・依存更新・運用 |
| `needs-decision` | **人間が決めないと進めない。AIはここで止まる** |

`needs-decision` は「AIが勝手に決めてはいけない」の印。
ライセンスの選定、外部サービスの採否、費用が発生する判断などが該当する。

増やさないこと。分類に迷うものは `chore` に入れる。

## Issue テンプレート

`.github/ISSUE_TEMPLATE/` に2種類ある。

| テンプレ | 使う場面 |
|---|---|
| **タスク**（`task.md`） | 実装・改修・調査。**受け入れ条件が必須** |
| **実機確認**（`verify.md`） | 開発環境から確認できないものを実機で見る |

実機確認テンプレは **確認する場所・見るもの・判定の分かれ目**を書く欄がある。
「効いている / 効いていない」を**両方**書くこと。片方だけだと、
変化が無かったときに「効かなかった」のか「見る場所が違う」のか区別できない。

### なぜ実機確認を Issue にするか

このプロジェクトは開発環境から地理院・OSM・Esri・気象庁・Open-Meteo の
**いずれにも到達できない**。加えて iOS Safari 固有の不具合は
ヘッドレスの Chromium では再現しない。
つまり「書けたが確認できていない」が構造的に溜まる。
`docs/status.md` に貯めると毎回読む量が増えるので、Issue へ逃がす。

## TODO の3層

| 期間 | 置き場 | 誰が管理 |
|---|---|---|
| 今このセッション内 | Claude Code 内蔵の TODO | AI（ファイルに書かない） |
| 数日〜数週間 | **GitHub Issues** | 人間 |
| いつか / 要確認 | `docs/status.md` の「未完・要確認」表 | 両方 |

- コード内の `// TODO` は **Issue番号必須**（`// TODO(#44): …`）。番号なしTODOは禁止
- **「未完・要確認」が10行を超えたら Issue 化して減らす**
  （`docs/status.md` を80行以内に保つため）

## コミットメッセージ

日本語のまま、先頭に prefix を付ける。

```
feat: 凡例をチャート下段へ移動
fix: 風速の単位取り違えを修正（km/hをm/sとして扱っていた）
docs: 引き継ぎメモを status.md に分割
refactor: 天気記号の描画を drawWeatherGlyph に集約
chore: uPlotを1.6.32に更新
test: スクラバーのスモークテストを追加
```

| prefix | 対象 |
|---|---|
| `feat:` | 機能追加 |
| `fix:` | 不具合修正 |
| `docs:` | ドキュメント |
| `refactor:` | 振る舞いを変えない整理 |
| `chore:` | 依存更新・運用・雑務 |
| `test:` | テスト |

prefix があると `git log --oneline --grep='^fix'` で**事故履歴だけ**追える。

### 粒度

**「ここで止めてもアプリが壊れていない単位」**で分ける（`CLAUDE.md` の「段階ごとにcommit分割」）。

### Issue との紐付け

- コミット末尾に `Refs #44`
- PR本文に `Closes #44`

## ブランチ

- `main` は PR 経由必須（直 push しない）
- 作業ブランチ: `claude/<issue番号>-<短い英語>`（例 `claude/44-legend-position`）
- **マージ済みブランチは使い回さず作り直す**

```bash
git fetch origin main
git checkout -B claude/44-legend-position origin/main
```

⚠ **この手順は「main が実態である」ことが前提。**
2026-08-07 に main が42コミット遅れた状態でこれを実行し、
衛星機能が存在しないコードを読んで誤答する事故が起きた。
前提が崩れると事故るので、`.claude/hooks/session-start.sh` の
ブランチ鮮度チェック（起動時に `origin/main` との差を出す）とセットで運用する。

## マージ（確認なしでよい範囲）

**CI（`smoke`）が緑なら、確認を取らずにマージしてよい。**
ただし次のどれかに触れる変更は、緑でも**必ず人に確認する**。

| 触れたら確認するもの | なぜ |
|---|---|
| ABC評価（`abcScore` / `abcScoreInv` / `judgePoint` / `THRESH`） | **判定が静かに変わる。** 画面上は普通に見えるので気づけない → ADR-0005 / ADR-0006 |
| `areas.json` の座標・標高 | 同上。座標ズレは判定を甘くする側に効く → #13 |
| `sw.js` / `manifest.webmanifest` / `icons/` | **悪い版が端末に貼り付く。** キャッシュとインストールに影響する |
| 外部の情報源を足す・送信先が増える | 相手方の利用条件・CORS・レート（#14）に関わる |
| 院内情報・施設名・個人名が入りうるもの | **このリポジトリは public。取り返しがつかない** → ADR-0009 |

要するに **「見た目とUIの改善はそのまま、判定と配信と公開範囲に触るものは確認」**。

### 確認が要るのは「戻せないもの」

push とマージは `git revert` で戻せる。だから上の線引きに収まるなら確認は要らない。
**戻せないのは次のもので、これらは必ず確認する。**

- **公開**（public なので一度出たものは消えない）
- **ファイルの削除・上書き**、履歴の書き換え（force push・rebase 済みの押し直し）
- **外部への送信**（新しい送信先が増えるもの）

⚠ **戻すのは安いが、公開されたものは戻らない。**
`git revert` 1コミットで Pages が再デプロイされ1分ほどで戻るが、
`git push --force` でも `refs/pull/*` は消せない（実際にこれでリポジトリを作り直した）。
**「戻せるから」で公開範囲の判断を緩めないこと。**

⚠ **開発環境から公開URLに到達できない**（プロキシが403）。
ただし**「配信されたか」だけは機械で分かる**ようになった（下記）。
判断が要る「使い勝手として直っているか」は依然として人しか見られない。

（2026-08-20 に合意。それ以前は毎回確認していた）

## デプロイ後の確認（`公開URLの検証`）

マージすると `Pages へデプロイ` が走り、その成功を受けて
`.github/workflows/verify-live.yml` の **`deliver` ジョブが自動で走る**。
公開URLを取ってきて `sotoki_v4.html` の sha256 と突き合わせるだけの検査で、
**外部を1つも叩かない**。赤が出たら意味はひとつ——**まだ配信されていない**。

⚠ **#27 はこれが無くて往復2回になった。** 「標高が出ない」の原因は不具合ではなく
**マージし忘れ**だった。「直したはずです」と言う前にここを見ること。

同じワークフローの **`browser` ジョブは手動実行のみ**（`workflow_dispatch`）。
実ブラウザで起動し、Nominatim・地理院・標高タイルを**実際に叩く**。

**⚠ `sotoki_v4.html` の検索まわり・外部URL・CORSに関わるものを変更したら、
マージ後に `browser` を手で回して結果を報告すること。**
自動では走らないので、**回さなければ誰も確かめない**。これがこの分け方の唯一の弱点。

なぜ手動だけにしたか（2026-08-20）:

- Nominatim の制限は**IP単位**で、Actions のランナーは他人のCIと共有のIPを使う。
  こちらの行儀と無関係に絞られうる
- 自動で回すと、赤の意味が「壊した／相手が落ちた／IPが絞られた」に割れる。
  **対応不要な失敗通知が定期的に届く検査は、そのうち誰も見なくなる**
- 手で回しても「叩けるか」という情報は同じだけ得られる。
  自動にして得るものより、偽の赤で失うものの方が大きいと判断した

⚠ **`browser` を `workflow_run` に広げない・`schedule` を足さないこと。**
戻すのは `if:` 一行なので、必要になったらいつでも戻せる。

⚠ **どちらも実機確認の代わりにはならない。** iOS Safari とホーム画面のPWAは
Chromium とは別物で、このリポジトリはiOS特有の不具合を2回踏んでいる。

## タグ

リリースごとに打つ。

```bash
git tag v4.77.0
git push origin v4.77.0
```

単一HTML構成なので、**タグさえあれば「あの時動いていた版」を1ファイルで取り出せる**。
現状バージョンは HTML 内にしか無いので、打つ価値が高い。

- 版数は `sotoki_v4.html` 内の表記と合わせる（下段・凡例行の右端に出ているもの）
- 打つのは `main` にマージされたあと
- ドキュメントだけの変更では打たない
