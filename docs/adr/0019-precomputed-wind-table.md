# ADR-0019: 風の細分化の表を Actions で前もって作り、Pages で配って端末で読む

- ステータス: 採用
- 日付: 2026-10-17

## 背景

「尾根と沢の細かい地形で風の流れを細かく見たい」（利用者・2026-10-15）。予報の風は約11km格子で、尾根と沢の差は出ない。
風を地形に合わせて細分化するには流れの方程式を解く必要があり、WindNinja（米国農務省林野局）の質量保存の解法で
谷川・上越国境（一辺 32km・升目 60m）を1方位解くのに数十秒かかる（Actions の4コア・`experiments/windninja/README.md`）。

ADR-0018 は地形の図（CS立体図風）について「保留: サーバー（Actions）で画像を作って配る」とし、
端末の速さで足りたので CS立体図風では採らなかった（`docs/decisions.md` 2026-10-12）。

## 決定

- 風の細分化の表（風向8方位 × 「範囲の平均の地上10m風の何倍か・何度曲がるか」）は、**Actions（`windninja.yml`）で山域ごとに前もって作り、
  `data/wind/<山域id>.png` と `.json` に置いて Pages で配る**。端末はそれを取って読み、判定の風に掛けて塗る（案A・`docs/requirements_wind_downscale.md`）
- ADR-0018 の保留を開くのは**この風の表に限る**。地形の図（CS立体図風・赤色立体図風など）は ADR-0018 のとおり端末で描き、Actions で画像を作らない
- 表は手動実行（と作り方を変えた非 main への push）で作り、PR で入れる。地形は変わらないので定期実行はしない
- 端末への控えは `sw.js` に手を入れない（案 a）。同じサイトのものとして本体の控えに入る

## 理由 / 検討した代案

- **却下: 端末で解く** … 1方位で数十秒（4コアの Actions）。端末で毎回解くのは重すぎ、地形は変わらないので毎回解く意味も無い
- **却下: 運動量の解法（OpenFOAM）で風下の陰まで出す** … 急な山で発散して使えなかった（findings-04）。陰は v4.177.0 の「風の当たり方」で見る
- **却下: 最初から 51山域ぶん作る** … 生成物は git の履歴に残り、消すにはリポジトリの作り直しが要る（ADR-0009）。谷川だけで試し、実機で良ければ足す
- **却下: 表を `experiments/` に置いたまま読む** … Pages は `experiments/` を配らない（`pages.yml`）
- **保留: `sw.js` で `data/wind/` をタイルの控え（150MB・LRU・取り直さない）へ回す（案 b）** … 試す段では山域1つで足りる。山域を増やす・圏外で困るときに開く（`sw.js` に触れるので確認が要る）
- **却下: 16方位で作る** … 質量保存の解は逆向きの風で倍率・曲がりとも同じ（findings-03）ので、0〜157.5° の8方位で全方位を引ける

## 影響

- `data/wind/` は **Pages で配られる（公開される）**。置くのは計算結果（倍率・曲がり）と、範囲・峰の名前（`areas.json` と同じもの）だけ
- 表示の数字の出どころとして **WindNinja が増える**（外部の情報源の区分）。端末からの送信先は増えない（表は自分の Pages から取る）。
  出典は「地理院タイル（標高タイル）を加工して作成」「WindNinja（米国農務省林野局）で計算」。WindNinja はパブリックドメイン＋BSD で、同梱はしない（Actions でビルドして使うだけ）
- 本体の控えに入るので、**開くたびに裏で取り直す**（谷川で PNG 1.98 MB・450×3600・2026-10-17）。`sw.js` の `CACHE_VERSION` を上げると消え、
  **更新の直後は圏内で一度開くまで圏外では出ない**
- 表の形式（PNG の R・G・A の意味・方位の並び・`peakRatio`）を変えたら、端末の読み手と JSON の `encoding` を一緒に変える
- ⚠ 範囲の取り方で倍率は 1〜2 割変わる（findings-02）。範囲は全山域で一辺 32km に固定し、山域ごとに変えない
- ⚠ 倍率は**推定**で、山の稜線での実測による検証はまだ無い（利用者の携帯風速計で比を測る案・README「検証の手段」）
