# ADR-0011: 判定に使う風の層を、モデル格子の標高で決めない

- ステータス: 採用
- 日付: 2026-09-07
- 関連: ADR-0006（山頂高度の気圧面風）の**安全弁だけを置き換える**、
  ADR-0005（風速の単位）、PR #56

## 背景

利用者の報告から発覚した。**2026-09-06 の至仏山（2,228m）で、
表示より現地の風が明らかに強かった。**

前線に向かう南西の暖湿流が強く、同日16:05に「東北も7日夜にかけて線状降水帯発生の
可能性」、19時に「東海・関東・東北で大雨災害に警戒」が発表されている荒天日だった。

過ぎた日の予報値を引き直して突き合わせた（`scripts/probeWind.mjs`）。

| 2026-09-06 の至仏山 | 最大 |
|---|---|
| **アプリが判定に使った風** | **4.55 m/s（終日A）** |
| 850hPa（約1,460m） | 16.39 m/s |
| **800hPa（約1,950m）** | **22.78 m/s** |
| 700hPa（約3,010m） | 16.53 m/s |

800hPa に下層ジェットが立っており、**モデルは正しく、アプリが読んでいなかった**。
体感と合うのは 22.78 m/s の方で、これは C になる。

### 原因は解像度ではなく、ADR-0006 の安全弁

ADR-0006 は「山頂がモデル地形より `WIND_LEVEL_MIN_RISE`（100m）以上高いときだけ
気圧面の風を使う」という安全弁を置いていた。気圧面が地中になり、無意味な外挿値を
拾うのを防ぐためである。

至仏山は **モデル地形 2,133m / 山頂 2,228m → 差 95m**。**5m 足りずに弁が働き、
地上10m風へ落ちていた。**

⚠ **これは至仏山だけではなかった。** 110峰を数えたところ
（`scripts/probeWindGap.mjs`、1リクエスト）:

| | |
|---|---|
| 安全弁で地上10m風に落ちる峰 | **109 / 110** |
| ランキングと詳細画面で使う風が食い違う峰 | **109** |

⚠ **ADR-0006 を書く発端になった皇海山も落ちていた。**
2026-08-10 の調査ではモデル地形 **1,405m**（山頂との差739m）だったが、
2026-09-07 に同じ地点を引くと **2,127m**（差17m）を返す。

**Open-Meteo が返す `elevation` の意味が変わった。** 標高の数字だけが山頂に寄り、
**風は地上10m風のまま**である（至仏山で 10m が 4.55、800hPa が 22.78）。
`pickWindSource` が「`elevation` は風の場が立っている地面の高さだ」と仮定していた
その前提が、こちらの知らないうちに崩れていた。

### 画面によって判定が割れていた

ランキングは山頂標高を指定して取るため `elevation` が返らず、
`pickWindSource(p.elev, null)` と呼んでいた。つまりモデル標高を渡していない。
本体の関数をそのまま動かして確かめた:

```
詳細画面   pickWindSource(2228, 2133) → ground（flat）… 4.55 m/s → A
ランキング pickWindSource(2228, null) → level 800hPa … 22.78 m/s → C
```

**同じ日の同じ山が、ランキングでは C、詳細画面では A。**

## 決定

**`pickWindSource` から `modelM`（モデル格子の標高）の引数を外す。
見るのは山頂の標高だけにする。**

- 残す安全弁は **「いちばん低い気圧面（925hPa＝約760m）より下なら地上10m風」だけ**
- 詳細画面・ランキング・峰の再取得の3か所すべてが同じ決め方になる
- ⚠ **`judgePoint` / `abcScore` / `abcScoreInv` は1行も変更しない。**
  `THRESH` の閾値も変えない。**変えるのは入力データの選び方だけ**（ADR-0006 と同じ姿勢）
- `state.elevation` 自体は残す。標高表示の予備（`displayElevation`）と、
  突風の補助リクエストで地形条件をそろえるのに使っている

## 理由 / 検討した代案

### なぜ引数ごと外すか

値を渡さないだけなら、`modelM` の分岐は**誰も通らない死んだコード**として残る。
「モデル標高を見る」という**間違った前提がコードに書いてある**状態が続き、
いつか誰かがまた渡す。**引数から消せば、渡そうとした時点で気づく。**

⚠ テストでも `pickWindSource(2144, 2127)` と余計な引数を渡し、
結果が変わらないことを見ている（黙って昔の挙動に戻らない）。

### 検討して却下した案

- **❌ しきい（100m）を下げる**
  数えた結果は「50mで15峰、25mで71峰」。⚠ **どこに置いても Open-Meteo が返す
  数字の意味に依存し続ける**ので、同じことがまた起きる。今回の失敗は
  「100が大きすぎた」ではなく「その数字を見たこと」なので、値の調整では直らない。
- **❌ 10m風と気圧面風の大きい方を採る**
  ADR-0006 で既に却下している。山頂がモデル地形より低い場合に地中の外挿値を拾う。
- **❌ 地形加速の係数を掛ける**
  報告の分析で挙がった案。⚠ **22.78 m/s で体感は十分説明がつく**ので、
  いまは要らない。係数を足す前に、**読むべき層を読む**のが先。
  乖離の実例を貯めてからでなければ、係数は当て推量になる。
- **❌ `elevation=` をリクエストに渡す**
  ADR-0006 で「風には効かない」と実測して結論済み。今回も確かめ直し、
  風速は1点も変わらなかった。**再提案しないこと。**
  `scripts/probeWind.mjs` は毎回この確認を出力する。

## 影響

**判定が変わる。** 110峰のうち109峰で、詳細画面が読む風が地上10m風から
山頂高度の気圧面風になる。⚠ **多くの場面で判定は厳しい側（A→B、B→C）へ動く。**
バックカントリー向けの道具としては、これが本来の姿である
（ADR-0006 が直そうとした「危険側へのズレ」がそのまま残っていた）。

ランキングの判定は**変わらない**（もともとこの決め方だった）。
食い違いが消えるのは詳細画面の側である。

## この判断が崩れたら気づけるようにしたもの

- `tests/smoke_wind.js` — モデル格子の標高が山頂の17m下でも 800hPa を読み、
  判定が C になること。詳細画面とランキングが同じ層を選ぶこと。
  ⚠ **落ちた理由（`reason`）まで見る**（`kind` だけだと撤回した弁で落ちても気づけない）
- `scripts/probeWind.mjs` — 峰と日付を指定して過ぎた日の予報値を引き直す。
  `elevation` を渡すと風が変わるかも毎回確かめ直す
- `scripts/probeWindGap.mjs` — 110峰のモデル標高との差を1リクエストで数える。
  ⚠ 判定の分かれ目は本体から切り出して動かす（書き写さない）
