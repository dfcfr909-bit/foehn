# ADR-0001: 単一HTML構成を維持する（バンドラを入れない）

- ステータス: 採用
- 日付: 2026-08-07（記録日。方針自体は本アプリの初期から継続）

## 背景

ナギナビの本体は `sotoki_v4.html` 1ファイル（約3,400行 / 157KB）。
JS・CSS・SVGがすべてこの中に入っており、ビルド工程が存在しない。
デプロイは GitHub Pages への静的配信（ADR-0003）で、ファイルを置けばそれが本番になる。

一方でファイルは伸び続けており、AIに全文を読ませるとそれだけでコンテキストを大量に消費する。
「そろそろ分割すべきでは」という提案が繰り返し出てくる状況にある。

## 決定

**当面は単一HTML構成を維持し、バンドラ（Vite / webpack / esbuild 等）を導入しない。**
分割の判断は `sotoki_v4.html` が **4,000行を超えた時点**で改めて行い、
そのときは本ADRを置換する新しいADRを書く。

## 理由 / 検討した代案

- **なぜ単一HTMLか**
  - ビルド工程がゼロなので、GitHub Pages に置いた `sotoki_v4.html` が
    そのまま本番の実体になる。「手元では動くがビルド後に壊れる」という層が存在しない
  - リリースごとにタグを打てば、**タグさえあれば「あの時動いていた版」を1ファイルで取り出せる**
  - 実機（iPhone Safari）で踏む不具合が多い作りなので、
    ソースと配信物が1対1であることの調査価値が高い

- **却下: バンドラ（Vite等）を導入してソースを分割する**
  - 依存とビルド設定という「アプリ本体と無関係に壊れるもの」が増える。
    このプロジェクトの不具合はほぼ全て実機のレンダリング側（iOS SVGフィルタ、
    Leafletのpane、canvas汚染）で起きており、バンドラはそこを1つも解決しない
  - GitHub Pages は静的配信なので、バンドラを入れるなら GitHub Actions での
    ビルド＆デプロイが必須になる。デプロイ経路が増えるのは移行の意図（ADR-0003）に反する

- **却下: 「分割するならバンドラが要る」という前提そのもの**
  - 誤り。GitHub Pages は静的配信なので `<script type="module" src="src/chart.js">` が
    そのまま動く。**ビルド工程を増やさずに「単一HTML」→「HTML + ESM数本」へ移行できる**。
    将来分割するときはこの道を採る（バンドラ導入とは別の判断）

- **却下: いますぐ ESM 分割する**
  - 3,400行の時点では、分割で得られるコンテキスト削減より、
    `docs/spec/code_map.md`（関数索引を置いてgrepで飛ぶ）の方が費用対効果が高い。
    行数が増えてから改めて判断する

## 影響

- **バンドラ・トランスパイラ・npm依存をアプリ本体に足さないこと。**
  `tests/` と `scripts/` は Node で動くので別扱い（ここは npm を使ってよい）
- ライブラリはCDNか `vendor/` 同梱で持ち込む（uPlotの扱いは ADR-0002）
- 本体を読むときは全文読みを避け、関数索引 → grep → 部分読みの順で当たること
- 4,000行を超えたら分割の是非を判断する。**そのときは本ADRを編集せず、新しいADRを書く**
