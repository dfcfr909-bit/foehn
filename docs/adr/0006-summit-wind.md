# ADR-0006: ABC評価の風速は「地上10m風」ではなく「山頂高度の気圧面風」を使う

- ステータス: 採用
- 日付: 2026-08-10

## 背景

利用者の報告から発覚した。**明日（2026-08-11）の皇海山（2,144m）を、てんくらは C、
ナギナビは終日 A と判定していた。**

Open-Meteo（`jma_seamless`）を実際に叩いて突き合わせたところ、原因が特定できた。

| 項目 | 8/11 17時の値 |
|---|---|
| `windspeed_10m`（**判定に使っていた値**） | **2.73 m/s** |
| `wind_gusts_10m` | 17.90 m/s |
| `wind_speed_850hPa`（1,460m） | 4.47 m/s |
| **`wind_speed_800hPa`（1,950m）** | **21.02 m/s** |
| `wind_speed_700hPa`（3,010m） | 28.86 m/s |

応答の **`"elevation": 1405.0`** が決め手だった。

- モデルの中では、この地点の地面は **1,405m**。皇海山の山頂 2,144m より **739m 低い**
- 1,405m 付近（850hPa=1,460m）の風は 4.47 m/s。地表摩擦でさらに落ちて 10m風が 2.73 m/s。
  **モデルとして内部矛盾は無い**
- **強い風が吹いているのは 1,950m 以上**（800hPa で 21 m/s）
- **実際の山頂はその速い層に突き出している。しかしモデルはその山頂の存在を知らない**

JMAモデルの格子（MSMで約5km）では孤立峰の地形が平滑化されて潰れるため、
**山頂の風は地上10m風では出ない。** これは特定の山の問題ではなく構造的なもので、
**モデル地形より高く突き出た山ほど、風の判定が系統的に甘くなる。**
バックカントリー向けの道具としては危険側へのズレになる。

突風 17.90 m/s が持続風 2.73 m/s の **6.5倍**という異常な比も傍証だった
（実在の地点では通常 1.3〜2倍）。突風は境界層の乱流で上空の運動量が降りてくる量を
見積もるため、**上空の風が強いこと**を間接的に示していた。

## 決定

**ABC評価に渡す風速（`d.wind`）を、山頂高度に最も近い気圧面の風に差し替える。**

- ⚠ **`judgePoint` / `abcScore` / `abcScoreInv` のコードは1行も変更しない。**
  `THRESH` の閾値も変えない。**変えるのは入力データの質だけ**
- 山頂高度は **峰と分かっていれば `areas.json` の `elev`（`state.summitElev`）を最優先**、
  無ければ国土地理院DEM（`state.demElevation`）、ランキングは `peak.elev`
- **山頂がモデル地形より高くないときは従来どおり地上10m風を使う**
  （気圧面が地中になり無意味な外挿値を拾うため）
- 気圧面の風が取れなかったときは10m風に落とすが、**そのことを画面に明示する**
- 表示する風速・風向も同じ値にそろえる（判定と表示が食い違わないようにする）

## 理由 / 検討した代案

### なぜ気圧面の風か

風は標高でダウンスケールできない。気温は気温減率で補正できるが、
**風速には物理的に単純な高度補正が無い**。モデルが持っている「その高度の風」を
直接読むのが唯一まっとうな方法になる。

### 検討して却下した案

- **❌ `elevation=2144` をリクエストに渡す**
  最初に疑ったが**効かない**。Open-Meteo の `elevation` は統計的ダウンスケール用で、
  **気温には効くが風速には掛からない**。実際に標高を渡しても `windspeed_10m` は変わらない。
  「標高を渡せば直る」は誤り。**再提案しないこと。**
- **❌ `THRESH` の風速閾値を下げて帳尻を合わせる**
  これは **ADR-0005 でやって失敗した対症療法そのもの**。あのときも「判定が厳しすぎる」と
  誤診して閾値を緩め、原因（km/h と m/s の取り違え）を隠してしまった。
  **入力が間違っているときに閾値をいじってはいけない。**
- **❌ 突風（`wind_gusts_10m`）を判定に使う**
  現実に近い値ではあるが、突風は「瞬間値」であって持続風の閾値（`THRESH`）と意味が違う。
  同じ閾値に入れると基準が二重になる。`judgePoint` の変更も要る。
- **❌ 上下2層から線形内挿する**
  なめらかにはなるが、気圧面の高度は標準大気の目安値なので**精度の割に複雑**。
  最寄り1層で足りる。
- **❌ 10m風と気圧面風の大きい方を採る**
  安全側に倒れて分かりやすいが、**山頂がモデル地形より低い場合に地中の外挿値を拾う**
  危険がある。結局は例外処理が要るので、最寄り1層＋安全弁と変わらない。
- **❌ 補助リクエスト（`fetchSupplemental`）で取る**
  当初はここで取る想定だった（突風・気圧面雲量と同じ経路）。だが
  **`jma_seamless` が気圧面の風を返すことを実測で確認した**（best_match と値が完全一致）ため、
  **本体のリクエストに含める**方が良い。理由は3つ:
  1. モデルが混ざらない（気温はJMA・風は別モデル、を避けられる）
  2. 通信が増えない
  3. **判定が後から変わらない。** 補助は非同期なので、先に A を出してから C に化ける。
     安全に関わる表示が遅れて覆るのは避ける

### なぜ「最寄り1層」か

皇海山 2,144m に対し 800hPa（1,950m）は差 194m、700hPa（3,010m）は差 866m。
最寄りを選べば十分近い。層の境目で不連続になるが、
**判定は3段階（A/B/C）なので、その粗さに対して層の切り替わりは問題にならない。**

## 影響

- **ランキングの見え方が一変する。** いま A の山域の多くが B / C になる。
  これが正しい姿だが、「判定が厳しくなった」という報告が来ても**閾値を戻さないこと**
  （ADR-0005 と同じ罠）
- **表示される風速の意味が「地上10mの風」から「山頂高度の風」に変わる。**
  ポップアップに高度を添えて、どこの風か分かるようにする
- `state.demElevation`（地理院DEMの実測標高）が**判定の入力になる**。
  これまでは表示専用だった。取得できないと10m風に落ちるので、
  **DEMの取得失敗を黙って握りつぶさないこと**
- ⚠ **DEMだけに頼らないこと（実機で踏んだ）。** `areas.json` の皇海山の座標は
  山頂から**5.2km**（ほぼ真南）ずれており、DEMが斜面を読んで
  **静かに地上風の判定へ落ちた**。
  エラーは何も出ず、画面には「A / @地上10m」と出るだけなので気づけない。
  **峰と分かっているときは `areas.json` の標高を渡すこと**（`gotoPeak` / `pickMapPoint` の
  第4引数）。座標の精度に判定を依存させない。座標そのものの検証は #67
- ⚠⚠ **座標のズレは「標高が違う」だけで済まない。** 5.2kmもずれると
  **モデルの格子セルが変わり、予報そのものが別地点のものになる**。
  この件で最初に測った 800hPa 21.02 m/s も、実は皇海山ではない場所の値だった。
  標高を渡す仕掛けは**判定が甘くなる事故を防ぐだけ**で、座標の誤りを帳消しにはしない。
  **#67 の座標検証を「見た目の整備」と思わないこと**
- 地上風に落ちたときは**読んだ標高も画面に出す**（`@地上10m（山頂570m）`）。
  数字が無いと「なぜ地上風なのか」を実機で切り分けられない
- **新雪ランキング（`snowRanking.js`）は対象外。** ABC評価とは独立で、
  積雪の推定に地上風を使っているのは妥当（吹きだまりは地表付近の現象）
- `wind_speed_unit=ms` の指定は気圧面の風にも必要（ADR-0005 は引き続き有効）
