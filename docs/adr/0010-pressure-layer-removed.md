# ADR-0010: 計算した気圧配置レイヤーを外す（格子点APIでは総観規模を賄えない）

- ステータス: 採用
- 日付: 2026-08-20
- 関連: Issue #26（気圧配置）、Issue #14（Open-Meteo のレート）、ADR-0001（単一HTML）

## 背景

Issue #26 で「地図に高気圧(青)・低気圧(赤)と等圧線を出す」を実装した（PR #38）。
Open-Meteo の `pressure_msl` を画面の格子で取り、局所極値に H/L を置き、
marching squares で等圧線を引く方式。**新しい情報源は増やしていない。**

実機で3回指摘を受け、そのつど直した。

| 指摘 | 原因 | 直し方 | PR |
|---|---|---|---|
| 少し動かすと `HTTP 429` | 格子を**画面の四隅**から作っており、動かすたびに点の座標が変わってキャッシュが一度も効かなかった | 固定の升目に載せる・LRU・429で冷却 | #39 |
| おもたい | 等圧線を**線分ごとに**レイヤー化していた（108レイヤー） | 高さごとに1レイヤー（9レイヤー） | #39 |
| 輪郭が角張っている | 点数の上限に収めるため升目が3〜8度（300〜900km）まで粗くなる | 描画用に格子を4倍細かくする（Catmull-Rom） | #40 |
| 拡大すると消える | z8 を超えると描かない上限を入れていた | 打ち切りをやめ、常に24度四方で計算 | #40 |

個々は直った。**しかし残った評価が「実用に耐えない」だった。**

> 日本列島をもっと縮小できないと大まかな気圧配置と風の流れが把握しにくい。
> しかしそうするとデータが重すぎる。

## 何が根本の問題だったか

**⚠ 目的と手段が構造的に噛み合っていない。**

- **大まかな気圧配置を掴むには広い範囲が要る**（日本列島＋大陸＋太平洋）
- **広い範囲を格子点APIで取ると点数が増える**。点数はそのままレート（#14）に効く
- **点数を抑えると升目が粗くなる**。3〜8度＝300〜900kmでは、等圧線は多角形になり、
  低気圧の中心も1つの格子点に丸められる

補間（Catmull-Rom）で**見た目**は救えたが、⚠ **情報量は粗い格子のまま**で、
「掴みにくい」という評価は変わらなかった。

つまり **「格子点APIで総観規模の場を、閲覧のたびにブラウザから描く」という形自体が、
このアプリの制約（ブラウザから直接叩く・無料枠・単一HTML）と噛み合っていない。**
パラメータの調整で越えられる壁ではない。

## 決定

**計算した気圧配置レイヤーを実装から外す。**

- `MAP_WEATHER` から `pressure` を消し、関連する関数・CSS・テストを削除する
- **Issue #26 は開いたままにする**（諦めではなく、やり方を変える）
- 分かったことはこのADRと `docs/decisions.md` に残す

コードは `6249445`（PR #40 マージ後）に残っている。marching squares・
Catmull-Rom 補間・局所極値の判定は、やり方を変えても**そのまま使える部品**なので、
作り直す前に読むこと。

```bash
git show 6249445:sotoki_v4.html | grep -n 'pressureBox' -A 200
git show 6249445:tests/smoke_pressure.mjs
```

## 却下した案

**点数の上限を上げる。** レートに当たる（実際 429 を出した）。⚠ 上限は
利用者の回数を消費するので、**こちらの都合で上げてよい数字ではない**。

**折れ線を後から均す（Chaikin 等）。** 見た目は軽く直るが、⚠ **隣り合う等圧線が
触れたり交差したりしうる**。天気図として読めない絵を出すくらいなら出さない方がよい。

**気象庁の天気図を地図に重ねる。** ⚠ **投影法が違う。** 速報天気図は円錐図法などで
描かれた1枚の絵で、このアプリの地図（Webメルカトル）とは座標系が合わない。
四隅を揃えても中身の海岸線がずれ、**H の位置が数百km違って見える**。
行動判断に使う道具で位置のずれた気圧配置を重ねるのは、出さないより悪い。

## 次にやるなら（有望な順）

1. **事前に計算して配る。** GitHub Actions で1日数回だけ気圧の場を取り、
   軽い JSON か画像にして `data/` へ置く。閲覧者は**1ファイル取るだけ**。
   - レートは**自分たちのCIで1日数回に抑えられる**ので、格子をずっと細かくできる
   - このリポジトリには**同じ形の前例がある**（AI全国概況 `scripts/gen-outlook.mjs` ＋ Actions）
   - ⚠ 引き換えに**時刻を自由に動かせなくなる**（作った時刻ぶんしか無い）。
     いまの時刻スライダーと噛み合うかは要検討
2. **気象庁の天気図を「別パネルの1枚絵」として出す。** 地図に重ねない。
   → **2026-08-25 に実装した**（`#wxmap-overlay` / `docs/spec/ui.md`）。
   実測で `list.json` も画像も `access-control-allow-origin: *` が付いており、
   **一覧の取得も画像の表示もそのまま通った**。実況に加えて**24時間後・48時間後の
   予想天気図**まで配信されている。通信は**一覧1回＋画像1枚**だけで、
   格子点APIのような点数の問題が無い（これが上の三すくみを解いている）。
   - ⚠ **前線が描いてある**。気圧の場だけからは原理的に出せないので、これは大きい
   - 画像は `<img>` で出せば **CORS は要らない**（fetch や canvas 読み取りをしなければ）
   - ⚠ ただし「いつの天気図があるか」の一覧を引くには fetch が要る。CORS は**未確認**
   - 確かめるなら手元ではなく **Actions のブラウザジョブから実際に叩く**
     （開発環境からは気象庁に到達できない。プロキシ403）

## この判断を覆すとき

**格子点APIをブラウザから直接叩く形に戻すなら、新しいADRを書くこと。**
「点数を少し増やせば足りるのでは」は、ここで一度試して駄目だった道。
